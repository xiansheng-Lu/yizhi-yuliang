# 12 核心状态机详设

本册把 00-11 册中出现的所有关键状态对象落到可实现的状态机：每个状态的含义与超时出口、每条转移的触发方/守卫条件/副作用/发出事件、非法转移的处理。实现时状态机代码必须与本册转移表一一对应，禁止在业务代码里零散写状态赋值。

## 0. 通用约定

### 0.1 图例与转移表列含义

| 列 | 含义 |
|---|---|
| 起始状态 | 转移前对象必须处于的状态 |
| 事件/动作 | 触发转移的命令（用户请求、Worker 回调、定时器等） |
| 目标状态 | 转移成功后的状态 |
| 守卫 | 转移前必须全部通过的条件，任一不满足即拒绝 |
| 副作用 | 与状态更新同一数据库事务内完成的写库动作（含 outbox）；外部平台调用永远在事务提交后 |
| 事件 | 提交后投递的领域事件（写 outbox_events，由 SSE/Worker 消费） |

### 0.2 通用规则

1. 所有状态转移用条件更新实现：`update ... set status=:to, version=version+1 where id=:id and status=:from and version=:expected`，影响行数 0 时按"状态已变化/版本冲突"返回 409，不允许先查后无条件更新。
2. 每次转移追加一行状态流水（command_jobs 写 job_events；执行单写 execution_order_events；其他对象写各自 history 表），含 from/to/actor/reason/at。
3. 终态不可被普通自动事件改写。唯一显式重开例外是FAILED经safe-retry守卫→EXECUTING：沿用原申请/执行单，新增attempt并保留失败历史，必须重验当前策略/审批与目标；不能静默改态或复制执行单。人工对账定性走专用动作并留痕。
4. 状态机代码只接收枚举值，不接收前端透传的字符串状态；对前端的状态输出按本册第 2 节投影表过滤。
5. 所有时间字段为 timestamptz；超时出口统一由 scheduled_tasks 到期扫描驱动，不用进程内 sleep/ETA 长等待。

## 1. command_job 指令任务（前端 V1.0 契约 12 态）

这是对前端暴露的唯一任务状态机，字段与枚举严格等于前端 `command-job.ts`，不得增删状态。内部执行单的更细状态经投影后才能进入本状态机（见第 2 节）。

### 1.1 状态定义

| 状态 | 中文名（契约） | 含义 | 最长停留与超时出口 |
|---|---|---|---|
| DRAFT | 待对象与风险确认 | 已创建，等待用户确认对象与风控结论；BLOCKED 之外的可编辑态 | expires_at 到期由 expire_jobs 扫描置 EXPIRED（仅未受理单据） |
| PENDING_APPROVAL | 待审批 | 用户已确认，等待审批人 | 到期 EXPIRED |
| APPROVED | 已批准·未执行 | 审批通过，等待执行内核领取 | 短暂态；超过调度 SLA 未领取触发告警与补偿投递，不回退 |
| EXECUTING | 执行中 | 执行单已被领取，平台调用在途或请求结果未知 | 内部 UNKNOWN 期间投影停留本状态（见 2.3），由回读/对账推进，不做超时失败 |
| VERIFYING | 待核验 | 平台已受理（accepted=true），独立回读中 | 回读窗口结束仍 UNKNOWN 转人工对账，前端保持本状态 |
| SUCCEEDED | 已核验完成 | 终态。PLATFORM 回执 + accepted=true + 核验 MATCHED 三者齐备 | 终态 |
| FAILED | 失败 | 平台明确拒绝、核验确认未生效、或对账确认未执行 | 普通事件终态；仅safe-retry显式命令可重开并产生新尝试 |
| REJECTED | 已驳回 | 终态。审批人驳回 | 终态；修改后须重新创建任务 |
| CANCELLED | 已取消 | 终态。用户在可取消阶段撤回成功 | 终态 |
| EXPIRED | 已过期 | 终态。未在 expires_at 前完成确认/审批/未受理执行 | 终态；已被 Worker 领取的单据不得判过期 |
| BLOCKED | 风控阻断 | 终态（对本次申请）。风控结果 BLOCKED 且不可经修改放行 | 终态；修改参数后重新创建任务 |
| MANUAL_REQUIRED | 待人工交接 | 终态（系统侧）。直播开关播无推流授权等只能线下完成的动作 | 由人工线下处理，系统只记录交接，不允许用广告暂停等其他动作冒充完成 |

### 1.2 转移表（生命周期动作）

业务动作 action_type 有 7 个（CHANGE_DAILY_BUDGET/CHANGE_BID/SET_ROI_TARGET/PAUSE_AD_PLAN/RESUME_AD_PLAN/REQUEST_LIVE_START/REQUEST_LIVE_END），它们是任务载荷不驱动状态；驱动状态的是下列生命周期动作。

| 起始 | 生命周期动作 | 目标 | 守卫 | 同事务副作用 | 事件 |
|---|---|---|---|---|---|
| （无） | create（PC_MANUAL/MOBILE_COMMAND） | DRAFT 或 BLOCKED | 接口幂等键不冲突且载荷一致；对象归属在数据范围；回读 old_value；四时点风控之创建时全量检查；AUTOPILOT 来源对外一律拒绝（400） | 写 command_jobs、job_events、idempotency_requests(IN_FLIGHT→DONE)；风控 BLOCKED 直接终态 | job.created / job.blocked |
| （无） | 直播开关播且能力无推流授权 | MANUAL_REQUIRED | 动作是 REQUEST_LIVE_START/END 且账户动作能力非 AUTHORIZED | 同上，risk_summary.result=MANUAL_ONLY | job.manual_required |
| DRAFT | confirm（用户确认提交） | PENDING_APPROVAL | expected_version 匹配；未过期；确认时复检额度/冷却/对象版本；风控策略仍为最新版（否则 409 要求重新确认）；批准意图哈希固化 | 状态推进；额度增额动作写 budget_reservations(HELD) 与账本预占；写 outbox（等待审批，不入执行队列） | job.confirmed |
| PENDING_APPROVAL | approve | APPROVED | 审批人有 task.approve；申请人≠审批人（SERVER_POLICY 例外且留策略依据）；approved_version 与当前意图哈希一致；策略未在等待期变更 | approvals 留痕；写 outbox 触发执行投递 | job.approved |
| PENDING_APPROVAL | reject | REJECTED | 审批人有权限；expected_version匹配；V1不要求客户端尚未实现的comment | 释放该单HELD预占（RELEASED）；approvals留痕 | job.rejected |
| DRAFT/PENDING_APPROVAL/APPROVED | cancel | CANCELLED | 未被Worker领取且无SENT尝试；expected_version匹配；与领取使用同一条件竞争 | 释放HELD预占；执行单若有则同步CANCELLED；队列重投验证终态后丢弃 | job.cancelled |
| EXECUTING/VERIFYING | cancel | （拒绝） | 已领取/已受理，不允许以本地取消掩盖平台在途；409 | 无 | — |
| APPROVED | 执行内核领取 | EXECUTING | 目标守卫 fence 领取成功；执行前最后复检（现值、能力、意图哈希、审批未撤销） | 建 execution_order/attempt；守卫租约 | job.executing（投影） |
| EXECUTING | 平台明确受理 | VERIFYING | receipt PLATFORM + accepted=true | 落 platform_receipts；scheduled_tasks 安排延迟回读 | job.verifying（投影） |
| EXECUTING | 平台明确拒绝 | FAILED | 错误分类完成 | 释放 HELD 预占；写 error（retryable 按分类） | job.failed |
| EXECUTING | 请求结果未知 | EXECUTING（不转移） | 超时/连接中断 | attempt=UNKNOWN；守卫 quarantined；建 reconciliation_task；error 投影 RESULT_UNKNOWN/retryable=false（对前端仍在执行中） | job.unknown（内部） |
| VERIFYING | 核验 MATCHED | SUCCEEDED | 独立回读比对一致（金额按整数分、ROI 按平台精度、布尔按状态映射） | 预占 SETTLED 且账本 B+=delta；守卫放行；记录 verified_at | job.succeeded |
| VERIFYING | 核验 MISMATCH（复读到期后确认） | FAILED | 已排除平台刷新延迟 | 预占不结算；异常队列+资金类高优告警 | job.failed |
| VERIFYING | 回读持续 UNKNOWN 超窗口 | VERIFYING（不变） | — | 转 reconciliation_tasks，前端持续"待核验/结果未知" | — |
| DRAFT/PENDING_APPROVAL/APPROVED | expire扫描 | EXPIRED | 过expires_at且未领取/无SENT；与Worker领取条件竞争；领取前也检查未过期 | 释放HELD预占；执行单若有则同步CANCELLED并记EXPIRED原因 | job.expired |
| FAILED | safe-retry | EXECUTING | 仅 FAILED（非 UNKNOWN 投影）；错误分类 retryable=true；原幂等键无在途；现值与申请前一致或差异可解释；动作在重试白名单（资金增加类默认不进） | 不新建申请；新建 execution_attempts（attempt_no+1，新平台稳定请求键）；守卫重新领取 | job.retry |

### 1.3 对前端的历史流水要求

每次状态转移向 `history` 追加 `{status, at, detail}`，detail 使用中文可展示文案（如"审批通过，等待执行"），但不携带原始异常堆栈。`risk_summary.checks` 必须逐条真实输出，不得为空数组。

## 2. execution_order 内部执行单与投影

### 2.1 内部标准十态

`PENDING_APPROVAL / PENDING / EXECUTING / VERIFYING / EFFECTIVE / FAILED / UNKNOWN / CANCELLED / PARTIAL / MANUAL`

| 状态 | 含义 |
|---|---|
| PENDING_APPROVAL | 执行单已生成但审批未完成（command_job 在 PENDING_APPROVAL 时内部可已有影子单） |
| PENDING | 审批通过，等待 Worker 领取（对应前端 APPROVED） |
| EXECUTING | Worker 已领取，平台调用在途 |
| VERIFYING | 已受理，回读中 |
| EFFECTIVE | 回读 MATCHED，执行确定生效（对应前端 SUCCEEDED） |
| FAILED | 确定未生效（拒绝/对账确认未执行/确认 MISMATCH） |
| UNKNOWN | 内部态：请求结果未知或回读长期不可得；不暴露给 V1 前端 |
| CANCELLED | 未受理前撤回成功 |
| PARTIAL | 批量/多目标中部分生效（一期无批量投放，本状态保留给创编多子对象场景，出现时必须附逐项结果） |
| MANUAL | 只能人工完成的交接动作 |

执行单转移：

| 起始 | 事件 | 目标 | 守卫与要点 |
|---|---|---|---|
| PENDING_APPROVAL | 审批通过 | PENDING | 审批留痕同事务 |
| PENDING | Worker 条件领取（fence+租约） | EXECUTING | 最后复检失败则直接 FAILED（资格类）或退回等待（暂时不可用，不重发） |
| EXECUTING | accepted=true | VERIFYING | 落回执，排回读 |
| EXECUTING | 明确拒绝 | FAILED | 分类错误码 |
| EXECUTING | 超时/中断 | UNKNOWN | 不重发；租约失效也不重新写平台，只恢复对账调度资格 |
| VERIFYING | MATCHED | EFFECTIVE | 额度结算同事务 |
| VERIFYING | 到期确认 MISMATCH | FAILED | 异常队列 |
| VERIFYING | 回读不可得 | UNKNOWN | 建对账任务 |
| UNKNOWN | 对账查到受理证据 | VERIFYING | 续走回读，不重复下单 |
| UNKNOWN | 对账确认未执行 | FAILED | 释放预占，附依据 |
| UNKNOWN | 长期无法定性 | UNKNOWN（挂起） | 异常面板挂起，通知人工；绝不自动重放 |
| FAILED | 显式safe-retry | EXECUTING | 同一申请/执行单、新attempt；白名单/可重试/无在途/现值/当前策略和审批全部复检；不自动重开 |
| PENDING | 取消成功 | CANCELLED | 平台未受理 |
| PENDING_APPROVAL/PENDING/EXECUTING | 判定仅能人工 | MANUAL | 直播无授权等 |

### 2.2 execution_attempts 尝试状态

`PENDING → SENT → ACK_ACCEPTED / REJECTED / UNKNOWN`；每次重试新增一行 attempt_no，登记 platform_request_key（平台稳定幂等号）。重投递先读 attempts：存在 SENT 后无终态证据的在途尝试时，只允许查询，禁止再次发起写请求。

### 2.3 verification 核验状态

`PENDING / MATCHED / MISMATCH / UNKNOWN`。回读按 1/3/10 分钟退避，窗口内首次 MISMATCH 不判死（排除平台刷新延迟）；到期由 scheduled_tasks 驱动定性。效果类指标（ROI 是否变好）永远不作为参数核验依据。

### 2.4 内部态到前端 12 态的投影表

| 内部事实 | command_job.status | execution_receipt 表达 |
|---|---|---|
| 审批中 | PENDING_APPROVAL | null |
| PENDING | APPROVED | null |
| 调用在途 | EXECUTING | accepted=null、verification=PENDING |
| 请求结果未知 | EXECUTING | accepted=null、verification=UNKNOWN、error.code=RESULT_UNKNOWN、retryable=false |
| 已受理回读中 | VERIFYING | accepted=true、verification=PENDING/UNKNOWN（附最后核验时间） |
| 对账确认受理 | VERIFYING | accepted=true、续走回读 |
| EFFECTIVE | SUCCEEDED | accepted=true、verification=MATCHED、observed_value 回值 |
| 确认未执行/拒绝/MISMATCH | FAILED | verification=MISMATCH 或 null + error |
| CANCELLED/MANUAL | CANCELLED / MANUAL_REQUIRED | — |

未来公共协议新增 RECONCILING/UNKNOWN 必须前端类型、校验器、OpenAPI、UI 联合升级，后端不得私自扩枚举。

## 3. approvals 通用审批

前端契约内嵌 approval 状态：`NOT_REQUESTED / PENDING / APPROVED / REJECTED`，字段 actor_id/decided_at/method(MANUAL|SERVER_POLICY)/approved_version。

| 起始 | 事件 | 目标 | 守卫 |
|---|---|---|---|
| NOT_REQUESTED | confirm | PENDING | 风控要求审批（REVIEW_REQUIRED 或策略强制） |
| PENDING | 审批人通过 | APPROVED | 审批分离；approved_version 与意图哈希一致；策略未变更 |
| PENDING | 审批人驳回 | REJECTED | V8意见按各契约校验；既有V1客户端无comment字段，需必填时先联合升级 |
| PENDING | 策略版本在等待期升级 | PENDING（不转移，拒绝本次决定） | 批准/驳回动作返回 409，要求用户按新策略重新确认 |
| PENDING | 申请人取消/单据过期 | REJECTED（system原因CANCELLED/EXPIRED） | 内部事件actor_kind=SYSTEM；对V1的approval.method=null，不新增不兼容枚举 |

预算上调、扩大消耗、暂停重要计划三类即使 AUTOPILOT 也强制人工审批，SERVER_POLICY 不得静默放行。审批人解析：申请单显式审批人 > 账户/企业审批角色配置 > 企业 OWNER。

## 4. 额度账本与预占

budget_ledgers 单行聚合（B=confirmed_total_minor，R=reserved_increase_minor，limit_minor，version）；budget_reservations 状态机：

| 起始 | 事件 | 目标 | 同事务动作 |
|---|---|---|---|
| （无） | confirm 且通过 `B+R+delta<=limit` 行锁校验 | HELD | R+=delta，写预占行 |
| HELD | 核验 EFFECTIVE | SETTLED | B+=delta、R-=delta |
| HELD | 驳回/取消/过期/确认未执行 | RELEASED | R-=delta |
| （无增额预占） | 减额动作MATCHED | 不创建HELD | 直接经额度服务持锁按核验事实调减B，写额度变动记录；不创建违反delta>0的负预占 |
| HELD | UNKNOWN | HELD（不动） | 不释放、不结算 |
| SETTLED/RELEASED | 任意 | 终态 | 纠错只能经额度应用服务串行入账并写差异，不直接改数字 |

## 5. target_execution_guards 目标守卫

每个可写目标（账户×平台对象）一行，字段 fence（单调递增栅栏）、lease_owner、lease_until、state：

| 状态 | 含义 | 转移 |
|---|---|---|
| IDLE | 无在途写 | 条件领取（fence 比对成功）→ LEASED，fence+1 |
| LEASED | 某Worker持有租约 | 核验/对账定性并结算后→IDLE；租约过期仅允许恢复者查询attempt，SENT/UNKNOWN转QUARANTINED，不能直接释放给新写；证明未发送才可重新领取 |
| QUARANTINED | 存在 UNKNOWN 在途 | 对账定性前一直保持；任何新写领取直接拒绝（409 TARGET_QUARANTINED）；定性后按结果 → IDLE |

同目标顺序由数据库守卫保证，不依赖队列顺序或 Redis 锁。

## 6. 消息与调度状态

### 6.1 outbox_events

`PENDING → PUBLISHED`；publisher confirm 成功置 PUBLISHED；不可路由/confirm 失败保持 PENDING 由 flush_outbox 高频补偿。投递只做事件状态修改，绝不重新触发业务副作用（Worker 侧 inbox 去重）。

### 6.2 consumer_inbox

`RECEIVED → PROCESSED`。先登记唯一键consumer+event_id；只有已PROCESSED才可重复直接ack。RECEIVED但未完成的重投必须检查attempt/守卫：未发送且具备领取资格可恢复；SENT/UNKNOWN只查询/对账；资格暂不可得则持久化恢复调度后再ack。不能因inbox行存在而丢弃任务，也不能把恢复调度当作再次调用平台的资格。

### 6.3 scheduled_tasks

`DUE → CLAIMED → DONE / FAILED / RESCHEDULED`；条件领取带租约，失败可退避 RESCHEDULED，超过 max_attempts 进死信并告警。回读、过期扫描、对账退避全部走本表。

### 6.4 reconciliation_tasks

`OPEN → INVESTIGATING → RESOLVED`，RESOLVED 必须带 resolution（CONFIRMED_EXECUTED/CONFIRMED_NOT_EXECUTED/MANUAL_CLOSED）与证据；MANUAL_CLOSED 仅有权限的人工可操作且写审计。

## 7. 内容生成状态（generation_jobs / generation_steps）

generation_jobs：`QUEUED → RUNNING → WAITING_PROVIDER / WAITING_REVIEW → SUCCEEDED / FAILED / CANCELLED`。

| 状态 | 进入条件 | 出口 |
|---|---|---|
| QUEUED | 运营在 SOP 步骤发起生成，参数与成本预估已确认 | Worker 领取 → RUNNING |
| RUNNING | 已向 NEXORA（或模型供应商）提交，等待即时结果 | 同步成功且需人工确认 → WAITING_REVIEW；已提交但回读未明 → WAITING_PROVIDER；明确失败 → FAILED |
| WAITING_PROVIDER | 供应商已受理，结果未回（轮询/回调等待） | 回调或轮询得到成片 → WAITING_REVIEW；超时按 external_job_id 查询，绝不重复发起付费调用；确认供应商未受理 → FAILED |
| WAITING_REVIEW | 产出候选，等待运营确认 | 采纳 → SUCCEEDED（产物登记 content_asset 并挂接 SOP 步骤）；放弃/重做 → 可回到 QUEUED（新 job）或 CANCELLED |
| SUCCEEDED/FAILED/CANCELLED | 终态 | FAILED 透传供应商原因；实际费用 actual_cost_minor 回写 |

generation_steps（复杂创作分步：商品资料→卖点→脚本→分镜→图片→视频→字幕→审核）：`PENDING → READY → RUNNING → WAITING_REVIEW → DONE / SKIPPED / FAILED`。某步重做只失效依赖其输出的下游步骤，已人工确认的独立结果保留（依赖关系显式存表，不靠目录约定）。

## 8. 分析与报告状态

- analysis_tasks：`QUEUED → RUNNING → SUCCEEDED / FAILED`；进度 progress 只反映真实阶段；SUCCESS 时生成不可变 analysis_results。
- report_drafts：`DRAFT → IN_REVIEW → PUBLISHED`；draft_versions 每次保存一行（乐观锁），PUBLISHED 后冻结为 published_reports，再修改产生新草稿。发布链接 token 可吊销、可设过期。
- 周期守卫：日报需 1 天、周报连续 7 天、月报完整自然月数据覆盖，不足时任务直接 FAILED（原因 DATA_COVERAGE_INSUFFICIENT），不允许降级生成。

## 9. 授权与能力状态

### 9.1 provider_authorizations

`ACTIVE → EXPIRED / REVOKED`；refresh_token 成功刷新维持 ACTIVE 并轮换令牌；连续刷新失败降级为 EXPIRED，相关账户写能力同步降级；管理员主动断开 → REVOKED。令牌密文带 key_version，轮换期间旧版本仅用于解密。

### 9.2 capability_assertions（六阶段）

每阶段一条断言，result `PASS / FAIL / UNKNOWN`，六阶段（PATH_VERIFIED → SCOPE_GRANTED → ACCOUNT_AUTHORIZED → BACKEND_INTEGRATED → SCHEMA_VERIFIED → EXECUTION_VERIFIED）不可跳级：前序非 PASS 时后续断言无效。执行能力必须六阶段全 PASS 才允许写；任一阶段过期或重新核验失败，账户能力视图立即降级并通知前端 connectors 集合。

### 9.3 sync_runs

`RUNNING → SUCCEEDED / PARTIAL / FAILED`；PARTIAL 表示部分游标成功，下一轮从确认的最小游标续跑。

## 10. 非法转移与错误口径

| 情形 | HTTP | 错误码 |
|---|---|---|
| 状态已被他人推进、expected_version 不符 | 409 | VERSION_CONFLICT（返回当前对象供前端展示差异） |
| 事件在当前状态不允许（如 VERIFYING 取消） | 409 | ILLEGAL_TRANSITION |
| 目标处于 QUARANTINED | 409 | TARGET_QUARANTINED |
| 风控策略版本过期 | 409 | POLICY_VERSION_CHANGED |
| 终态对象再次操作 | 409 | RESOURCE_TERMINAL |
| 状态机收到未知枚举 | 500（内部断言失败，不向前端透传） | INTERNAL_STATE_ERROR |

状态机实现集中在各域的 `*_state_machine.py`，转移表用声明式数据结构表达（from/event/to/guard 列表），Service 层只调用 `transition(obj, event, actor, payload)`，不允许出现裸 `obj.status = ...`。

## 11. R00-03 冻结采用（状态机侧）

本册涉及资金、领取竞争与恢复的转移，以[R00-03 资金与恢复冻结规格](../contracts/R00-03-资金与恢复规格.md)为准（机器清单 `../contracts/funds-recovery-contract.json`）。本节只声明采用关系、补齐原文缺失处并给出可执行谓词，不另立一套状态。

| 冻结决定 | 本册对应章节 | 采用方式 |
|---|---|---|
| D-01 单一领取闸 | §1.2 转移表 | cancel/expire/claim 使用同一条条件更新谓词，只有一方成功，其余 409 |
| D-02 预占存在区间 | §1.2 confirm 行、§4 额度账本 | 预占在 confirm 创建；DRAFT 的释放为幂等空操作；减额不创建预占 |
| D-03 safe-retry | §1.2 FAILED 行、§2.1 | 沿用原申请与原执行单，只新增 attempt 行与新平台请求键 |
| D-05 守卫隔离 | §1.2 VERIFYING 行、§5 目标守卫 | 执行单进入 UNKNOWN 一律转 QUARANTINED，回读不可得与提交不可得一致 |
| D-06 证据等级 | §4 额度账本、§5 目标守卫 | 释放/结算/解除隔离分别以 E1/E2 为充分条件，E0 一律禁止 |
| D-08 inbox 恢复 | §6.2 consumer_inbox | 按 inbox×attempt×守卫三元组查冻结判定表 |
| D-10 终态与唯一重开例外 | §0.2 通用规则、§1.1 状态定义 | UNKNOWN 不是终态；已被领取的单据不得判过期 |
| D-11 谓词一致 | §0.2、§10 非法转移 | 条件更新 + 影响行数 0 即 409；禁止裸赋值与私自扩枚举 |

补齐原文缺失处：

1. §1.2 三处"与Worker领取使用同一条件竞争"落实为同一条谓词（`status='APPROVED'` + `version=:expected` + 无 SENT 尝试 + 未过期），先获得行锁者胜出，其余按 409 处理；因此不会同时出现 CANCELLED 与 EXPIRED。
2. §1.2 `DRAFT` 的 cancel/expire 行"释放HELD预占"为**幂等空操作**（DRAFT 阶段不存在预占），不得报错、不得创建负额预占。
3. §1.2 "VERIFYING 回读持续 UNKNOWN 超窗口"行补齐守卫后果：执行单进入 UNKNOWN 并把目标守卫转 QUARANTINED，预占保持 HELD，转 `reconciliation_tasks` 后**保持 UNKNOWN 与 QUARANTINED**，不降级为 FAILED。
4. §4 "HELD | UNKNOWN | HELD（不动）"与 §5 "SENT/UNKNOWN转QUARANTINED"统一为：释放/结算/解除隔离的充分条件按 E1/E2 证据等级判定，不得按状态字符串直接释放。
5. §6.2 的 inbox 恢复判定表以冻结规格的逐格表为准；`inbox=PROCESSED` 才可直接 ack，其余必须先持久化恢复调度再 ack，且 inbox 行本身不构成平台写资格。
6. §10 错误口径补充：隔离态新写领取返回 409 `TARGET_QUARANTINED`；`UNKNOWN` 期间禁止重发写请求。
