# 15 关键链路时序与事务边界

本册用时序图把系统最容易出错的九条链路画到"哪一步在哪个事务里、崩溃在各点如何恢复"的粒度。图中 T1/T2 标注数据库事务边界，Q 表示入 RabbitMQ 队列，OB 表示写 outbox_events，SSE 表示事件投影通知。所有外部 HTTP（平台、LLM、NEXORA）一律在事务外执行。

## 0. 事务编码约定

1. API async 与 Celery prefork 共用同一套 Service/状态机代码，差别只在 session 工厂（async psycopg / 同步 psycopg）；业务规则不出现第二份。
2. 一个用例最多三类数据库事务：读事务（短）、"决策事务"（状态推进+预占+outbox，短、不跨外部调用）、"落账事务"（外部结果回来后记账，短）。
3. 事务开始先 `set_config('app.current_tenant', ..., true)`；连接归还池即失效。
4. 锁顺序固定：租户 → 额度桶 → 目标守卫 → 业务单（按 id 排序），避免死锁。
5. 消息只携 ID 与 event_id，工作数据回库读取；消息处理结束（外部结果落账后）才 ack。

## 1. 登录与会话吊销

```mermaid
sequenceDiagram
  participant U as 浏览器
  participant API
  participant PG as PostgreSQL
  participant R as Redis
  U->>API: POST /v1/auth/login
  API->>PG: T1 校验密码/验证码、失败计数
  API->>PG: T1 写 sessions(revoked_at=null)、审计
  API->>R: 缓存会话主体(TTL)
  API-->>U: Identity + Set-Cookie
  Note over U,API: 登出/管理员停用/改密
  U->>API: POST /v1/auth/logout
  API->>PG: T2 revoked_at=now()（事实源）
  API->>R: 删除缓存（加速）
  API-->>U: 200 + command-job-v1.0信封(data=null)
```

失败点：T2后删缓存失败不影响吊销。每次受保护请求先经受限认证仓储校验PG会话/成员状态；不能只相信尚未到TTL的缓存，也不能声称缓存版本会“自然”知道库已变更。认证引导权限见09册；Redis仅缓存可重建主体属性，不可用时回源。

## 2. 指令→确认→审批→执行→回读（正常路径）

```mermaid
sequenceDiagram
  participant U as 运营/老板
  participant API
  participant L as 额度服务
  participant PG
  participant MQ as RabbitMQ
  participant W as Worker(execute)
  participant PF as 广告平台
  participant SSE
  U->>API: POST /v1/command-jobs（幂等键）
  API->>PF: 只读回读 old_value（事务外，缓存现值）
  API->>PG: T1 风控全量检查+建单(DRAFT)+幂等账+OB(job.created)
  API-->>U: DRAFT + risk_summary
  U->>API: confirm（expected_version）
  API->>PG: T2 复检额度/冷却/版本；select for update 锁额度桶
  API->>PG: T2 B+R+delta<=limit 通过 → 预占 HELD，单→PENDING_APPROVAL，OB
  API-->>U: PENDING_APPROVAL
  U->>API: approve（审批人≠申请人）
  API->>PG: T3 审批留痕、意图哈希校验、单→APPROVED、执行单 PENDING、OB(order.dispatch)
  API->>MQ: 投递器发布 order.dispatch，publisher confirm
  MQ->>W: 投递（至少一次）
  W->>PG: T4 inbox 登记；守卫条件领取(fence) IDLE→LEASED；最后复检 → EXECUTING
  W->>PF: 提交变更（platform_request_key）
  PF-->>W: 受理回执 accepted=true
  W->>PG: T5 落 receipt/attempt；VERIFYING；scheduled_tasks 排回读；OB(job.verifying)
  W->>SSE: job.changed
  Note over W: 30-120s 后 platform 队列执行回读
  W->>PF: 独立只读查询
  PF-->>W: observed_value
  W->>PG: T6 比对 MATCHED → EFFECTIVE/SUCCEEDED；预占 SETTLED；B+=delta,R-=delta；OB
  W->>SSE: job.changed(SUCCEEDED)
```

要点：T2/T3/T5/T6都是独立短事务；平台调用在T4提交后。守卫领取失败不能直接推定任务已完成：检查inbox/attempt，只有PROCESSED可直接ack，其余在途走持久化恢复/对账，未发送走受控重新调度，确保任务仍可见。T1回读old_value失败按UPSTREAM_ERROR拒绝创建，不信前端现值。

## 3. UNKNOWN 与崩溃恢复（资金安全核心）

```mermaid
sequenceDiagram
  participant W as Worker
  participant MQ
  participant PG
  participant PF
  W->>PG: 领取后 attempt=SENT
  W->>PF: 写请求（超时/连接中断/进程在响应前崩溃）
  Note over W: 结果未知：禁止重发写请求
  W->>PG: T1 attempt=UNKNOWN；receipt(accepted=null,verification=UNKNOWN)
  W->>PG: T1 守卫→QUARANTINED；reconciliation_task(OPEN)；scheduled 退避查询；OB
  Note over MQ,PG: 消息此时才 ack；崩溃未 ack → MQ 重投递
  W->>PG: 重投递：inbox 去重 + 查到 UNKNOWN 在途 attempt → 不再调写接口
  loop 退避 1/3/10 分钟
    W->>PF: 用 platform_request_key / receipt 号只查不写
  end
  alt 查到受理证据
    W->>PG: T2 单→VERIFYING，续走回读（可能 MATCHED→EFFECTIVE）
  else 查到未执行
    W->>PG: T3 单→FAILED；预占 RELEASED(R-=delta)；任务投影 FAILED
  else 长期无法定性
    W->>PG: 保持 UNKNOWN；异常面板挂起；人工 MANUAL_CLOSED 需证据+审计
  end
```

崩溃点对照：

| 崩溃位置 | 恢复行为 |
|---|---|
| T3 提交后、发布 MQ 前 | outbox 补偿投递，命令不丢 |
| MQ confirm 前进程死 | 事件仍 PENDING，flush_outbox 重发；inbox 保证不重复执行 |
| 平台返回前 Worker 死 | 消息重投；attempt 在途判重，只查不写 |
| 平台成功、落 T5 前死 | 同 UNKNOWN 路径，查询定性，不重复下单 |
| T6 落账后、ack 前死 | 重投后 inbox 已 PROCESSED，直接 ack |

前端全程看到：EXECUTING + RESULT_UNKNOWN（可解释文案与核对时间），不出现失败闪烁，也不能再点提交（423 LOCKED/409 TARGET_QUARANTINED）。

## 4. MISMATCH 与平台限流

```mermaid
sequenceDiagram
  participant W as Worker
  participant PF
  participant PG
  W->>PF: 首次回读
  PF-->>W: 与 new_value 不一致
  Note over W: 不立即判死，按能力声明复读（排除平台延迟）
  loop 有限次
    W->>PF: 延迟复读
  end
  W->>PG: 仍不一致 → FAILED(MISMATCH)；预占不结算；异常队列高优告警；OB
  Note over W,PG: 平台 429/限流式错误
  W->>PF: 平台拒绝（限流式）
  W->>PG: attempt 不落终态；scheduled 按平台退避 RESCHEDULED；不占用户重试次数
```

MISMATCH 不自动"补一刀"覆盖；参数式错误（余额不足、非法值）不重试；资金增加类默认不在 safe-retry 白名单。

## 5. OAuth 授权与六阶段取证

```mermaid
sequenceDiagram
  participant A as 管理员
  participant API
  participant PF as 平台
  participant W as Worker(platform)
  participant PG
  A->>API: GET /connections/oauth/{provider}/start
  API->>PG: T1 写 state（绑定会话、短时、一次性）
  API-->>A: 302 平台授权页
  A->>PF: 同意授权
  PF->>API: callback(code,state)
  API->>PG: T2 校验 state 与会话
  API->>PF: code 换 token（事务外）
  API->>PG: T3 token AES-GCM 加密入库 provider_authorizations(ACTIVE)
  API->>W: OB → capability_probe
  W->>PF: 拉账户列表、校验 scope
  W->>PG: T4 逐阶段写 capability_assertions（不可跳级），聚合 account_capabilities；OB
  API-->>A: 连接详情（逐项能力，不返回 token）
```

回调与发起会话的浏览器无关（可换机完成），state 绑定的是发起管理员身份。令牌刷新：refresh_platform_tokens 按 provider+主体串行锁；刷新失败能力立即降级，写能力同步关闭并通知前端。

## 6. 平台数据同步管道

```mermaid
sequenceDiagram
  participant B as Beat
  participant W as Worker(platform)
  participant PF
  participant PG
  B->>W: sync_assets/reports（按账户排期）
  W->>PG: T1 sync_runs(RUNNING)；读取每资源确认游标
  loop 分页（受配额/并发限制）
    W->>PF: 带游标只读拉取（超时/429 退避）
    PF-->>W: 数据页 + 原始载荷
    W->>PG: T2 原始载荷存档；稳定字段 upsert；metric_facts 按唯一键 upsert；推进游标
  end
  W->>PG: T3 sync_runs SUCCEEDED/PARTIAL；新鲜度字段；OB(sync.completed)
```

一个 Worker 会话只处理一个租户上下文；PARTIAL 时游标只推进到已确认页。限流策略（QPS、错峰、熔断）按平台配置，熔断期同步任务 RESCHEDULED，不发告警风暴（持续阈值才告警）。页面请求永远读库，不被同步慢调用阻塞。

## 7. SSE 订阅、补发与重连

```mermaid
sequenceDiagram
  participant U as 浏览器
  participant API
  participant PG
  U->>API: GET /v1/events（Cookie, Last-Event-ID?）
  API->>PG: 校验会话与数据范围
  alt 携带 Last-Event-ID
    API->>PG: 读 event_projections where id > last and scope 可见 order by id
    alt 游标在保留期内
      API-->>U: 补发历史帧后保持长连接
    else 过旧
      API-->>U: event: resync
    end
  end
  loop 新事件
    PG-->>API: 投影落库（由 outbox 消费者写）
    API-->>U: 帧（25 秒无事件则 :ping）
  end
  Note over U,API: 断线 → 指数退避重连带最后 id；写请求不重放
```

权限撤销/租户切换：服务端检测到会话失效直接关闭流，客户端跳登录。投影由 outbox 消费事务写库，SSE 进程只是"读投影唤醒连接"，无状态、可多实例水平扩展（一期单实例也成立）。

## 8. 内容生成（NEXORA）与扣费未知

```mermaid
sequenceDiagram
  participant O as 运营
  participant API
  participant W as Worker(ai/media)
  participant N as NEXORA
  participant OSS as 对象存储
  participant PG
  O->>API: POST /content/generation-jobs（费用确认+幂等键）
  API->>PG: T1 generation_jobs(QUEUED)；幂等；OB
  W->>N: 提交生成（external_job_id）
  alt 同步返回受理号
    W->>PG: T2 RUNNING→WAITING_PROVIDER
  else 提交超时
    W->>PG: T2 仍 WAITING_PROVIDER；用幂等键/external 查单，绝不二次提交付费
  end
  N-->>W: 回调（或轮询取到结果）
  W->>PG: 回调幂等校验（provider+external_job_id 唯一）→ WAITING_REVIEW
  W->>OSS: 下载成片到私有桶
  W->>PG: T3 content_assets 登记；job 待确认
  O->>API: 预览后采纳
  API->>PG: T4 SUCCEEDED，result_asset_id、actual_cost_minor 回写，挂接 SOP 步骤
```

重复回调：唯一索引兜底，重复只回 200 不重复处理。已扣费但结果长期丢失：保持 WAITING_PROVIDER 并告警，人工凭供应商账单核对，不自动退款也不自动重发。

## 9. 分析报告生成与发布

```mermaid
sequenceDiagram
  participant U as 老板/运营
  participant API
  participant W as Worker(ai/media)
  participant PG
  U->>API: POST /v1/business-analysis/tasks（范围+维度+周期）
  API->>PG: T1 预检数据覆盖（日1/周7/月自然月）→ QUEUED；不足直接 422 DATA_COVERAGE_INSUFFICIENT
  W->>PG: T2 RUNNING；从 metric_facts 重新汇总（不取日比率平均）
  W->>W: AI 仅做章节叙述（引用证据 id），规则模板可降级
  W->>PG: T3 不可变 analysis_results + SUCCEEDED；OB
  U->>API: 编辑草稿（revision 乐观锁）→ 预览
  U->>API: 发布
  API->>PG: T4 生成 published_reports 冻结快照；随机公开 token（可吊销/可过期）
```

发布后的报告不可变；勘误发新版本。公开链接阅读接口不建会话、只校验 token 状态与过期时间，且受速率限制防爬。

## 10. 失败处理统一口径

1. 任何"写了库但外部结果未知"都走 UNKNOWN/WAITING_PROVIDER 挂起，不用超时当失败、不用重试赌幂等。
2. 所有补偿（outbox 补发、scheduled 到期、对账扫描）都是只推进状态的扫描器，频率可配且可暂停；它们不重新承载业务决策。
3. 队列不可用：API 写事务正常提交（事件在库），健康检查 readyz 失败以阻止扩容实例写入；恢复后积压按队列出清，监控积压年龄而不是任务数。
4. 每条异常分支须有审计/指标；故障演练见11册10.1及19册A17–A25/A33/A36。发送供应商请求前持久化我方请求键与SENT状态；外部ID未返回也必须可挂起核对，不能重新发付费请求。
