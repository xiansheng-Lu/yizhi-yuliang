## R00-01：保持现有客户端契约

现有52项请求矩阵见 `http-contracts.json`；实际54处调用、请求体推导类型和133个导出类型的完整字段声明见 `frontend-surface.json`；黄金样例见 `golden.json`。15份关键源码散列固定于矩阵（UTF-8/LF归一，兼容Windows/Linux换行），前端后续更新后必须重新核对，不能静默重写散列。05/14册是说明，TypeScript请求和校验器是现有兼容边界。供人审阅的逐接口核对表见[R00-01交付说明](R00-01-接口契约核对.md)。

- 所有JSON成功信封外层 `schemaVersion=command-job-v1.0`，包含非空requestId和data。200/202一样；退出200+data:null。
- 内层各用原版本：V1 `schema_version=1.0`；V8 `contractVersion=delivery-v8.0`；V9 `contractVersion=advertising-v9.0`；分析 `schemaVersion=business-analysis-v1`。

- Identity.workspacePages取routes.ts的customerPageIds；快照保留十二数组、API来源、scope和上海时区。没有平台数据允许合法空快照，未授权不放入他人店铺。
- 现有ApiClient不注入CSRF，也只按HTTP状态映射错误，尚不能展示完整业务码/details。这分别由F01/F02处理；不能用后端测试冒充双端通过。

### CSRF新增契约（F01待复核）

GET `/v1/auth/csrf` 使用成功信封返回 `{token, expiresAt}`，Cache-Control:no-store；仅精确允许的Origin可携凭证读取。未登录时下发HttpOnly的短期预认证cookie，服务端保存令牌摘要、有效期和用途；登录和发邮件码均提交X-CSRF-Token绑定此挑战。挑战不包含邮箱，不能用来判断邮箱存在。

登录成功撤销预认证挑战、轮换为绑定会话的新令牌。已登录GET同一路径返回该会话令牌；服务端只持哈希时，不可倒推出令牌，应签发并替换为新令牌（旧页拿到403后仅重新获取令牌，不自动重放原写请求）。登录/切租户/退出使旧令牌失效。会话cookie在生产Secure+HttpOnly+SameSite=Lax。优先同源反代，分域通过此JSON接口取得令牌，不假设JS能读API域cookie。

### V9异步素材新增契约（F11待复核，未对外开放）

现有POST `/v1/delivery/configuration/materials`立即要求最终SelectedResource，保持原行为约束，后端不能直接改成202任务。本轮为异步流程增加独立路径，待F11接线才启用：

1. POST `/v1/delivery/configuration/material-upload-tasks`，multipart包含现有context/file及clientRequestKey；202返回V9内层信封及task，task含taskId/clientRequestKey/state/version/resource:null。文件SHA256、完整账户上下文与原键绑定；相同键不同文件409。
2. GET同路径以product/accountId/clientRequestKey查询，或GET `.../material-upload-tasks/{taskId}`，两种都校验租户/账户/产品权限。
3. state为PENDING/PROCESSING/VERIFYING/SUCCEEDED/FAILED/UNKNOWN。SUCCEEDED才有resource及真实platformId/sourceMaterialId；UNKNOWN只查询，不允许客户端新键重传。上传成功和素材审核eligible分别表达；未审核不得可投放。

新内容API和公开报告路径仍按05/14/16册：内容文档/资产/SOP/生成位于 `/v1/content/`，公开发布页面独立随机token路径 `/p/{publicToken}`。后者不使用会话权限，也不能暴露内部草稿；到期/撤销立即拒绝。后续对应M3/M4卡补完整请求Schema和实测。

## R00-02：数据库、认证与调用模型

| 项 | 冻结决定 | 后续真实验收 |
|---|---|---|
| ID | 租户bigint，对外字符串；业务实体uuid，对外字符串；平台native_id独立 | M0-06空库升级 |
| 迁移顺序 | 扩展/角色→租户/全局身份→成员/会话/挑战→角色权限→店铺/账户/商品/场次目录→业务表→RLS/授权→后续事实/事件/分区 | 不使用create_all代替迁移 |
| 复合FK | 店铺/账户/商品/场次建立UNIQUE(tenant_id,id)；业务引用均用同二列FK。会话同时约束(tenant_id,membership_id,user_id)引用成员同三列唯一键；用户全局身份可挂多租户，不能强制users主租户=membership租户 | M0-08b跨租户插入/更新拒绝 |
| 系统模板 | 单独只读系统表或显式系统行策略；应用不能写系统行。不得用tenant_id=0代表未知身份 | M0-08a |
| 审计 | audit_logs按时间分区，PK(id,created_at)；应用仅INSERT/SELECT，无UPDATE/DELETE/TRUNCATE；认证事件写独立auth_events | M0-17 |
| 事实键 | tenant/provider/product_line/account/entity_kind/entity_id/SKU/live/attribution/currency/timezone/bucket/time共同定义可比行；缺失不写0，未知源更新时间不由抓取晚覆盖 | M1-10/11/12/13 |
| SSE | 锁租户watermark行，投影和递增同事务提交；tenant_seq是续传键，事务回滚不消费可见序号；不能用全局自增ID充当提交水位 | M4-09a |

### 认证角色与最小函数面

业务连接app_login无SUPERUSER/BYPASSRLS/CREATEDB/CREATEROLE，非表所有者；无租户上下文读业务为空、写拒绝。迁移与运维角色不放进应用配置。认证使用单独app_auth连接，只有auth schema的USAGE和以下函数EXECUTE，不授权基础表，也无通用SQL/任意tenant输入入口：

| 固定函数接口 | 最小返回或动作 |
|---|---|
| auth.credentials(normalized_email text) | 活跃身份的id和password_hash，仅供可信后端校验；失败统一响应 |
| auth.memberships(user_id uuid) | 已验证用户的活跃成员id/租户，须在密码/挑战校验后调用，不接收客户端任意user_id |
| auth.create_session(user_id, membership_id, token_hash, csrf_hash, expires_at, absolute_expires_at) | 在函数内复查成员/身份有效性与归属，插入会话；期限受服务端上限约束 |
| auth.resolve_session(token_hash text) | 会话及成员最小结果，必须检查撤销、滑动/绝对过期、用户/成员停用 |
| auth.renew_session(token_hash, expires_at, csrf_hash) / auth.revoke_session(token_hash) | 只更新同token对应会话；续期不能越过absolute_expires_at |
| auth.issue_challenge(email, purpose, digest, expires_at) / auth.consume_challenge(challenge, digest) | 内部次数/节流、一次消费锁；失败不泄露邮箱；不回明文验证码 |
| auth.record_event(email_digest, outcome, request_id, ip_digest) | 受限追加事件；归属可空，无业务tenant=0 |

实现这些函数的所有者使用单独NOLOGIN身份，跨租户访问仅授予所需认证表，固定search_path=pg_catalog并全限定表名，撤销PUBLIC EXECUTE，禁止动态SQL。若为FORCE RLS身份表使用BYPASSRLS函数所有者，必须NOLOGIN、不可SET ROLE给应用、且无业务表权限。函数本身不能向HTTP调用方暴露。具体DDL/函数实现与权限攻击测试属于M0-06/09/11，当前表格是接口规格，不是已执行迁移。

### API与Worker共用规则的确切方式

领域规则纯Python，无SQL/HTTP依赖。应用用例接受同步SQLAlchemy Session，由API在 `AsyncSession.run_sync(use_case, ...)` 中调用；Worker由同步Session直接调用同一use_case。两种会话都在调用前开启事务并参数化set_config(...,true)。run_sync中只允许SQLAlchemy数据库IO，外部HTTP/Redis/SMTP都在事务外；API使用async httpx，Worker使用同步适配器或独立asyncio.run，不能把阻塞外调塞入run_sync。引擎/池/Session不跨进程共享。

依据：[SQLAlchemy官方run_sync文档](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#running-synchronous-methods-and-functions-under-asyncio)。

## R00-03：资金和恢复的定性表

| 场景 | 数据库条件与结果 | 预占/目标守卫 | 下次动作 |
|---|---|---|---|
| 取消/过期与Worker领取竞争 | 同一行status+version+未领取/无SENT谓词；仅一个条件更新成功 | 取消/过期获胜才释放HELD；领取获胜则拒取消/过期 | 重投读事实，不重复领取 |
| 提交超时无受理证据 | attempt=UNKNOWN，前端EXECUTING、accepted=null、verification=UNKNOWN | 保留HELD并QUARANTINED | 只查询平台原请求键/对象并对账 |
| 已受理但回读未知 | 前端VERIFYING、accepted=true、verification=UNKNOWN | 保留HELD并隔离；租约过期不能解锁 | 回读，超窗口转人工 |
| 受理且独立回读MATCHED | 前端SUCCEEDED，PLATFORM回执、observed_value和verified_at齐全 | 同事务SETTLED、R减delta/B增delta，再解除守卫 | 不重发 |
| 回读MISMATCH | 观察窗口内继续回读；到期标FAILED且异常挂起，但不是“未执行”的证据 | 有受理证据仍保留预占和隔离 | 对账按实际值入账；确认未执行才能释放 |
| 明确拒绝/对账确认未执行 | FAILED，持久化拒绝/未执行依据 | 同事务RELEASED，守卫只在无其他在途后释放 | 若白名单safe-retry则完整复检 |
| safe-retry | 仅已定性FAILED+可重试+无在途+当前策略/审批/现值通过 | 同申请/执行单，新attempt_no、新稳定平台请求键；增额默认不允许 | 不是消息自动重放 |
| 外部改预算超过上限 | 将真实B写入账本并登记差异，不设B+R<=limit全局CHECK | 拒新增额，减额MATCHED才减少B | 告警/人工确认 |
| inbox重复RECEIVED | 不能直接ack，也不能重新取得平台写资格 | 检查attempt/fence；SENT/UNKNOWN仅恢复查询 | 持久化恢复调度后ack；仅PROCESSED可直接ack |
| 已付费生成丢受理号 | 调用前已持久化clientRequestKey和费用预占，UNKNOWN | 继续查原键/账单，禁止另键重复付费 | 无法定性待人工 |

首写放行需指定账户×动作×金额，真实只读、审批分离、异常可见、最小恢复及5次MATCHED按对应卡留证；本次开发授权不构成该许可。签字E08单列，Agent不代签。

## R00-04：执行与证据规则

`../evidence/task-status.json`只登记已领取卡的覆盖状态，未列卡为NOT_STARTED，未列门禁为NOT_PASSED。合法状态：IN_PROGRESS、IMPLEMENTED、TECH_VERIFIED、WAITING_REVIEW、BLOCKED、DONE；每条保存技术验证、三条DoD结果、未通过依赖/外部条件、实际证据与复核。

技术层已验证的纯规格可作为不涉及真实操作的工程准备输入；涉及未冻结双端差异的接口在F卡确认前不开放。R00等待BE/FE签字不冒充DONE；允许本轮已授权的M0工程入口和信封离线准备，台账明确标注依赖签字待完成。数据库/消息等I类依赖必须实测后再领取依赖其事实的实现，不以配置文件存在放行。

实际证据每卡 `../evidence/tasks/<ID>/README.md`，记录基线/环境/命令/预期与实际/三条DoD/范围/回滚/负责人复核。原101父任务不重复关闭，全部适用叶卡DONE才关闭。未执行live记NOT_RUN，缺环境记BLOCKED，跳过不记PASS。下一卡按20册拓扑及实际通过层级领取。
