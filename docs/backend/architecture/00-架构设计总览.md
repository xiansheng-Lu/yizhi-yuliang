# 易致·驭量后端架构设计总览

版本：V1.1（前端对齐评审修订稿）
日期：2026-10-26（Asia/Shanghai）
状态：已完成本轮代码对照评审与文档整改；实现、真实平台验证及上线门禁尚未完成
阅读对象：业务负责人、后端开发、前端对接、运维及未来交付实施人员。

本文是后端详设的入口，给出一句话结论、技术选型速览、文档地图和待拍板事项。各分册只展开自己的主题，跨文档的术语、端口、枚举以本总览第 4 节的"统一口径表"为准。

本轮评审结论：方向保留，契约/DDL/状态恢复规格须按链路收口。代码基线与问题证据见18册，资源估算、关键依赖、前端接入和验收以19册为准。17册保留任务ID，不等于对全部设计已放行。

## 1. 一句话结论

后端采用 **Python 3.13 + FastAPI 模块化单体**：一套代码仓库，按业务域划分强边界模块，API 进程与异步 Worker 分离部署；数据用 PostgreSQL 17（含 pgvector）加 Redis，任务消息走 RabbitMQ，平台对接全部经服务端连接器，AI 能力经统一 LLM 内核编排；一期支撑公司内部运营、服务商和老板的多组织使用，架构按"多租户 SaaS + 单租户私有化交付"双形态设计，后期开放或交付三方不需要重写。

本套详设是仓库历史文档《后端技术架构与实施设计 V1.1》（2026-10-22）的细化与替代，继承其全部核心决策（Python/FastAPI、模块化单体、平台连接器、审批风控核验、额度预占、Outbox、RabbitMQ、双形态交付），并基于最新的前端 V8/V9 契约、1818 条平台接口目录和 V9 多平台规划做了领域与表结构展开。差异取舍见第 7 节。

选 FastAPI 而不是 Django，核心原因是本产品后端的三件重头工作——平台异步对接、AI 大模型流式编排、长任务回读核验——都天然是异步 IO 场景，且前端已经沉淀了严格的 TypeScript 契约，FastAPI 的 Pydantic 模型与 OpenAPI 自动产出可以和前端契约直接对齐。内部运营管理后台用 SQLAdmin 补齐，不为此引入第二套 Web 框架。

## 4. 统一口径表（跨文档权威源）

本表是所有分册的术语和参数权威源，各文档引用此处，不各自表述。

### 4.1 基础约定

| 项目 | 约定 |
|---|---|
| 业务时区 | 统一 `Asia/Shanghai`，库内时间存 UTC，接口与 UI 按北京时间呈现 |
| 人民币金额 | 整数分（CNY minor）传输与存储，禁止浮点元入账；输入元仅在边界换算 |
| 微信豆 | 独立整数单位 `BEAN`，与人民币不换算、不相加 |
| ROI | 无单位正比值，汇总 ROI = 汇总 GMV ÷ 汇总消耗，不平均各计划 ROI |
| 缺失语义 | 缺失为 `null`，真实零为 `0`，二者不得互换；未接入显式声明 |
| 统计时间 | 指标归属日期与 `source_updated_at / fetched_at` 分开记录 |
| 接口信封 | 当前外层固定 `schemaVersion:"command-job-v1.0"`，含requestId/data；域版本置data内，失败见05册 |
| 服务端标识 | 业务请求优先使用驭量内部ID，平台原生ID单独存字段；部分V9资源明确带nativeId用于展示/校验，不得把它直接当可执行目标 |
| 内部版本头 | 投放工作区 `delivery-v8.0`、创编配置 `advertising-v9.0`、平台资源 `platform-workspace-v9.0`、任务 `command-job-v1.0` |

### 4.2 组织与平台标识

- 组织层级：`Tenant（企业/租户）→ BusinessEntity（经营主体）→ Shop（店铺）→ AdAccount（广告账户）`，另设多对多关联表表达真实世界里"一个店铺关联多个账户、一个主体拥有多个店铺"的情况。
- 平台提供方 `provider`：`tencent`（腾讯系）、`ocean`（巨量引擎）、`xhs`（小红书）、`wxshop`（微信小店经营）、`beans`（微信豆加热）。
- 产品线 `product_line`：`adq / wxpromo / beans / wxshop / ocean_marketing / qianchuan / dou_plus / local_push / juguang / redshop`。
- 前端八个连接器 `connector_id` 与上述映射：`adq→tencent/adq`、`wxpromo→tencent/wxpromo`、`beans→beans`、`wxshop→wxshop`、`qianchuan→ocean/qianchuan`、`douyinshop→ocean 抖店`、`juguang→xhs/juguang`、`redshop→xhs 电商`。
- 数据隔离最小键：`tenant_id + business_entity_id + shop_id + provider + product_line + account_id + native_object_id`。

### 4.3 任务与能力状态

- 中枢指令任务对前端保持 12 态不变：`DRAFT / PENDING_APPROVAL / APPROVED / EXECUTING / VERIFYING / SUCCEEDED / FAILED / REJECTED / CANCELLED / EXPIRED / BLOCKED / MANUAL_REQUIRED`。
- 新版执行单内部标准态：`PENDING_APPROVAL / PENDING / EXECUTING / VERIFYING / EFFECTIVE / FAILED / UNKNOWN / CANCELLED / PARTIAL / MANUAL`，两套状态的映射按前端 V8 契约第 6 节执行。
- 回读核验结果：`PENDING / MATCHED / MISMATCH / UNKNOWN`；只有 `PLATFORM 回执 + accepted=true + MATCHED` 才能对前端宣称成功。
- 能力可用性：`AUTHORIZED / UNAUTHORIZED / NOT_INTEGRATED / NOT_APPLICABLE / FORBIDDEN / ERROR`。
- 字段级状态（创编向导）：`PUBLIC / AVAILABLE / API_PENDING / AUTH_REQUIRED / NOT_APPLICABLE / UNCONFIRMED`。
- 能力六阶段凭证：`path_verified → application_scope_granted → account_authorized → backend_integrated → request_schema_verified → execution_verified`（对应前端 verification 七字段的聚合展示），每阶段留存证据（proof），任何 API 只有目录依据时默认不可执行。

## 5. 架构原则

1. 平台密钥、风控裁决、执行动作全部在服务端，浏览器只做交互和展示。前端 Mock 与本地草稿永远不能作为权限或真实数据的依据。
2. 钱的变更先取证、再审批、后执行、必回读。结果未知时宁可挂起对账，不做自动重放。
3. 能力是数据，不是代码开关。平台能不能做某动作，由能力注册表和授权证据回答，前端按钮的可用性由后端返回决定。
4. 平台数据不伪造。接口没接通就给准确空态，不用假数据、不做 Mock 回退冒充 API。
5. 模块边界先于功能速度。一期代码量不大时守住分层和依赖方向，后期才有资格按域抽服务。
6. AI 只在有证据边界处使用：解析用户意图、生成建议和内容草稿；凡是花钱、改计划的动作，必须回到人确认和执行内核，AI 不直接落刀。
7. 一套代码两种交付形态。多租户 SaaS 和私有化交付通过配置切换，不维护两套代码分支。

## 7. 与历史 V1.1 设计稿的关系

仓库版本库中保留着《后端技术架构与实施设计 V1.1》（2026-10-22，工作区文件已在之前的目录重整中移除，HEAD 仍可查）。本套详设对它"继承 + 展开 + 少量修订"，评审时可对照：

继承不变的核心决策：

1. Python + FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic，模块化单体，API/Worker 分进程。
2. Celery + RabbitMQ 任务投递（发布确认、持久队列、Quorum 高可用演进）；PostgreSQL 是业务与任务状态唯一事实源，Outbox + 到期任务表租约扫描兜底恢复。
3. 金额 BIGINT 整数分、ROI NUMERIC、意图哈希（intent_hash）、批准不可变载荷哈希、乐观锁版本。
4. 预算额度账本与预占（budget_ledgers / budget_reservations）、目标执行守卫（target_execution_guards）、执行尝试与平台回执分表（execution_attempts / platform_receipts）。
5. RLS 纵深隔离、应用账号无 BYPASSRLS、敏感表 FORCE RLS、复合外键 (tenant_id, id)。
6. 结果未知不重放：UNKNOWN 挂对账、有限回读退避、首次不匹配不立即判死。
7. 对现有 V1 客户端不直接发送新状态（UNKNOWN 兼容表达见 06 册）。
8. GenerationJob 与 CommandJob 分离、模型调用按能力端口封装、LiteLLM 按需引入、费用独立账本。
9. expand-contract 式数据库演进、恢复演练、商业化与计费后建。

本套详设的展开与修订：

| 主题 | V1.1 | 本套 | 理由 |
|---|---|---|---|
| Python 版本 | 3.13 兼容基线 | 3.13 明确定为基线 | 保持一致，B0 锁补丁版本 |
