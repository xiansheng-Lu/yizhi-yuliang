# 02 技术选型

本册给出后端技术栈的选型结论、对比理由和版本基线。原则：团队能驾驭、AI 生态友好、与前端契约贴合、运维成本与当前规模匹配；不为简历选技术，也不为想象中的大厂规模提前上重型设施。

## 1. 选型总表

| 层面 | 选型 | 版本基线 | 用途 |
|---|---|---|---|
| 语言 | Python | 3.13.x（B0 验证全部依赖后锁定补丁版本） | 业务后端唯一语言 |

## 2. 关键选择的理由

### 2.1 为什么是 FastAPI 而不是 Django

这是本栈最需要说清的决策。Django 是成熟稳妥的默认选择，Django Admin 对内部系统尤其诱人；但本项目后端的负载形态有三个鲜明特征：

1. **出站 IO 远多于入站计算**。每个业务动作几乎都伴随平台 API 调用或大模型调用，二者都是慢 IO：平台接口几百毫秒到数秒，LLM 数秒到数十秒。异步框架用少量进程承载大量在途请求，资源利用率显著优于 WSGI 同步栈。
2. **AI 流式交互是产品入口**。AI 驭量中枢的对话需要 SSE 流式返回；FastAPI 的 `StreamingResponse` 与异步生成器是一线能力，Django 需要叠加 Channels 才能体面支持。
3. **契约就是资产**。前端已有四份 TypeScript 契约，字段约束细（金额安全整数、ROI 正比值、联合类型 JobValue）。Pydantic v2 与 FastAPI 自动产出的 OpenAPI 可以直接对照前端契约维护，类型错误在框架层被拦截。

Django 的优势主要是 Admin 与"电池齐全"。对应解法：内部运营后台用 SQLAdmin（基于 SQLAlchemy 的 Admin，支持模型注册、权限、搜索），用户/授权/审计这类低频管理完全够用；认证、ORM、迁移、Admin 之外的 Django 电池（表单、模板、sites 等）在纯 API 后端里本就用不上。

放弃 Django 不是因为它不好，而是本产品"AI + 平台对接 + 长任务"的形态下，FastAPI 的契合度更高，且团队可以把精力放在业务内核上而不是框架适配层。

### 2.2 为什么是 SQLAlchemy 2.0 而不是 Tortoise/SQLModel

- SQLAlchemy 是 Python 生态事实标准，长期维护确定性最高，二期招人无压力。
- 2.0 的 async Core + 新声明式写法成熟，类型注解支持完整，mypy 可查。
- Alembic 迁移能力最可靠，JSONB、分区表、RLS 策略等 PostgreSQL 特性可以直接写原生 DDL。
- SQLModel 表层更甜，但本质是 SQLAlchemy 封装，复杂查询和迁移场景仍要回到底层，多一层不确定性。

Pydantic（接口模型）与 SQLAlchemy（持久化模型）分两套模型维护，不做合一。接口模型对外，持久化模型对内，中间用显式转换。多一层类换来边界清楚，避免平台原始字段直接泄漏到 API。

数据库驱动选 psycopg 3 而不是 asyncpg：psycopg 3 同时提供同步与异步 API，API 进程用 async 接口，Celery prefork Worker 用成熟的同步接口，一套驱动两种进程模型，RLS 的 `SET LOCAL` 租户上下文与事务行为完全一致；它也是 SQLAlchemy 2 官方首推驱动，并支持服务端预定义语句等调优手段。

### 2.3 为什么主库是 PostgreSQL 17

- **RLS（行级安全策略）**支撑多租户共享库方案：租户隔离不只靠应用代码自觉，数据库连接设置 `app.current_tenant` 后，漏写 tenant 条件的 SQL 直接查不到数据，是防越权的第二道闸门。
- **JSONB** 适合存平台原始载荷与能力快照：平台字段变化频繁，先原样落 JSONB，稳定字段再抽列，避免被平台字段变更拖着天天改表。
- **pgvector** 让 AI 检索（相似素材、对话长期记忆、诊断案例库）不用再引入一个向量数据库，一期规模内完全够用。
- 事务、约束、表达式索引、分区表能力完整，金额整数分和乐观锁版本号都有可靠支撑。

版本取 17：2026 年内 17 是扩展生态（pgvector 等）与云托管、私有化镜像都最成熟的稳定主线；云托管 PostgreSQL 18 若提供且 pgvector 等扩展通过实测，可直接采用，应用层不依赖任何 17/18 差异特性。自建 Compose 与交付环境不追新。

MySQL 不在考虑范围：RLS 与 JSONB 能力弱于 PostgreSQL，pgvector 无替代；团队也没有 MySQL 存量运维负担。

### 2.4 Redis 的职责与边界

Redis 承担：会话缓存（事实记录在 PostgreSQL sessions 表，Redis 只缓存会话主体，缓存丢失重新查库即可）、目标执行守卫的租约与互斥标记、接口与验证码限流计数、冷却期标记、热点能力与选项的短 TTL 缓存。

明确不用 Redis 做的事：不用它做业务数据持久层与任务状态事实源（任务、审批、费用、执行尝试全部以 PostgreSQL 为准，Celery result backend 关闭持久化结果依赖）、不用它存放平台令牌（令牌加密入 PostgreSQL，Redis 只缓存解密后的短时 access token）、不用 Redis Stream 承担业务消息（消息队列用 RabbitMQ）。

### 2.5 Celery + RabbitMQ

异步框架选 **Celery 5**：

- 本项目定时任务多且关键（各平台报表同步、令牌刷新、任务过期扫描、回读核验、Outbox 补偿），Beat 与成熟运维工具链（Flower、撤销、ETA、死信）价值大。
- Worker 内调用平台和 LLM 虽是异步 IO，但 Celery 任务函数可以是同步外壳内运行 `asyncio.run` 驱动异步 httpx 客户端，封装一个小工具即可，不构成实质障碍；Worker 使用同步 psycopg 与独立连接池，引擎在子进程启动后初始化。
- 失败重试、任务撤销、ETA 延迟核验（执行后 N 分钟回读）语义稳定，这些都是钱相关链路，优先用经过验证的设施。

Broker 选 **RabbitMQ** 而不是 Redis：执行链路的任务就是"钱"，需要持久队列、消息发布确认（publisher confirm）、不可路由回退、死信和成熟的高可用路径（三节点 Quorum）。Redis 做 Broker 在 AOF 故障与极端内存场景下的消息可靠性历史上有过争议，不值得为省一个容器去承担。一期单节点持久化 RabbitMQ 不宣称高可用，消息丢失兜底由 Outbox + PostgreSQL 到期任务表扫描承担（见 06 册）；高可用阶段升三节点 Quorum。长短任务分队列、平台账户有界并发、写任务不做无差别自动重试，具体纪律见 10 册。

### 2.6 为什么 AI 调用只认 OpenAI 兼容协议

国内主流商用模型（DeepSeek、豆包、通义、智谱）和自部署推理（vLLM、Qwen、Ollama）均提供 OpenAI 兼容接口。后端的 LLM 内核只写一套客户端，按模型配置切换 base_url、api_key、模型名，带来三个好处：

- 供应商可替换，比价与容灾，不被单一厂商绑定；
- 私有化交付时把 base_url 指向客户内网 vLLM 即可，业务代码零改动；
- 结构化输出（function calling / JSON mode）行为模式一致，指令解析的 Pydantic 校验逻辑通用。

### 2.7 管理后台：SQLAdmin

内部运营需要的后台操作：查用户与租户、封禁账号、查看成员关系、查看平台授权状态（不显示明文令牌）、查审计流水、查执行任务与回执、处理卡住的任务。这些用 SQLAdmin 注册模型即可满足，挂在 FastAPI 同一应用的 `/admin/` 路径，独立鉴权（仅平台管理员角色可入）。

不为内部后台单独开一个 Django 项目或前端工程，避免双框架、双部署。

## 3. 被否决的备选

| 备选 | 否决原因 |
|---|---|
| Django + DRF | 异步与流式弱，为 Admin 引入整套全家桶不划算 |
| Django + Ninja 异步补强 | 异步 ORM 与 ASGI 成熟度仍有坑，团队心智成本高 |
| Go（Gin/Fiber） | AI 与数据处理生态不及 Python，团队无 Go 积累 |
| Node/NestJS 同栈后端 | 与前端同语言有优势，但 AI/数据管道生态与快速试错效率低于 Python |
| MongoDB 主库 | 多表事务、口径严肃的财务型数据不适合文档库 |
| MySQL | 缺 RLS、JSONB、pgvector，多租户与 AI 检索成本高 |
| Kafka 一期上线 | 任务规模不需要日志型消息队列；RabbitMQ 已覆盖可靠任务投递，演进触发条件见 10 册 |
| 微服务（K8s + 多服务）一期上线 | 内部小规模团队维护不起，先用模块化单体验证边界 |
| LangChain 全家桶 | 抽象重、版本演进快、黑盒多；LLM 内核用薄封装自研。LiteLLM 可作为多模型适配的可选库放在内部端口之后逐项验证，不强制部署独立 Proxy；创作流程出现复杂分支与人工暂停时再评估 LangGraph，不提前引入 |
| 直接调平台 SDK（如有） | 各平台 SDK 质量与维护不一；统一用 httpx 实现连接器，行为可控、可测试、可审计 |

## 4. 依赖分组与工程基线

### 4.1 依赖分组

依赖在 `pyproject.toml` 中分组管理：

- 核心运行：fastapi、uvicorn[standard]、gunicorn、pydantic、pydantic-settings、sqlalchemy[asyncio]、alembic、"psycopg[binary]"、redis、httpx、tenacity、aiocircuit、argon2-cffi、cryptography。
- 任务与存储：celery（amqp 传输，随包自带 kombu/pyamqp）、boto3/aioboto3、sqladmin、aiosmtplib、jinja2（邮件模板）。
- AI：openai（OpenAI 兼容协议）、litellm（可选，按需逐项验证）、tiktoken（用量估算，可选）、pgvector 配套扩展（数据库侧）。
- 可观测：structlog、sentry-sdk、prometheus-client、opentelemetry-*（按需）。
- 开发：pytest、pytest-asyncio、anyio、httpx、testcontainers、ruff、mypy、pre-commit、ipython。

### 4.2 运行时基线

- Python 3.13，生产使用精简官方镜像（`python:3.13-slim`），uv.lock 锁定全量依赖与补丁版本后提交；B0 阶段必须完成 FastAPI、Pydantic、SQLAlchemy、psycopg、Celery 在 3.13 的集成验证。
- 统一 Windows 本地开发：开发机为 Windows，项目提供 PowerShell 启动脚本与 Docker Compose；Python 代码本身保持跨平台，路径一律 `pathlib`。
- 配置走环境变量 + `.env`（pydantic-settings 读取），区分 local/dev/staging/prod；密钥不入库，提供 `.env.example`。
- 编码与注释：源码 UTF-8，中文注释，不使用 emoji 与装饰性字符。

### 4.3 质量门禁

- `ruff check` + `ruff format`：风格与常见错误。
- `mypy`：核心域模块（执行内核、风控、连接器、金额处理）强制严格类型；接口模型全部标注。
- `pre-commit`：提交前自动检查。
- `pytest`：单元测试覆盖状态机、风控、金额换算、权限过滤、幂等冲突；集成测试用 testcontainers 起真实 PostgreSQL/Redis/RabbitMQ 跑迁移与消息确认恢复。
- CI（GitHub Actions）：安装、lint、mypy、测试、构建镜像四步，Windows 开发不影响 Linux 容器交付。

## 5. 客户端环境与网络拓扑要点

结合项目实际网络环境（国内业务平台 + 海外 AI 服务）：

- 腾讯广告（api.e.qq.com）、微信小店/微信 API（api.weixin.qq.com）、巨量、小红书接口均为国内直连，Worker 出口**禁止挂翻墙代理**，否则可能触发平台风控甚至鉴权失败。
- LLM 若使用海外 API，单独走可配置的出口代理，代理设置限定在 LLM 客户端的 httpx 客户端实例，不设置进程级全局代理，保证国内平台流量直连。
- Redis/PostgreSQL/RabbitMQ/MinIO 一期内网部署，不暴露公网（RabbitMQ 管理端口仅内网/VPN）；只有 API 的 443 与平台 OAuth/Webhook 回调地址对外。

## 6. 版本升级立场

- 小版本随 CI 滚动更新；大版本升级（FastAPI、Pydantic、SQLAlchemy、Celery）单独立项，先在 staging 验证迁移与契约。
- 应用层不维护旧版客户端兼容（产品前期团队可控）；数据库变更仍按 expand-contract 安全发布：迁移只做兼容性扩展（加表加列），应用发布并数据回填完成后再单独迁移清理旧结构，回滚应用不依赖回滚数据库迁移，避免"删列与旧实例并存"的事故窗口。
- 前端 schemaVersion 是对外契约，后端升级不得擅自改写既有信封版本；新版本字段新增接口或升级 schemaVersion 并与前端同步。
