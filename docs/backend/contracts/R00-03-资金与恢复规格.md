## 1. 冻结决定清单

### D-01 单一领取闸：取消/过期/领取唯一出口

`cancel`、`expire` 扫描、`Worker 领取` 三者在单据处于 `APPROVED` 时互斥。冻结要求：三者的条件更新**必须使用同一条谓词**，且只允许一方成功，其余返回 409。

```sql
update command_jobs
   set status = :to, version = version + 1
 where id = :id
   and status = 'APPROVED'
   and version = :expected
   and not exists (select 1 from execution_attempts where execution_order_id = :id and status = 'SENT')
   and expires_at > now()
```

- 胜出优先级是**行锁获取顺序**，不做业务优先级排序：先获得行锁的一方写入终态，其余因 `status`/`version` 条件不再命中而失败。
- 领取胜出后不得再以本地取消或过期掩盖平台在途：此时取消返回 409，已受理的写入由回读与对账定性。
- 取消先胜出则过期扫描不再命中（谓词要求 `status='APPROVED'`），因此**不会同时出现 CANCELLED 与 EXPIRED**。
- 过期扫描先胜出则单据进入 EXPIRED 终态，取消返回 409 `RESOURCE_TERMINAL`。
- 失败方的错误码取 `VERSION_CONFLICT` / `RESOURCE_TERMINAL` / `ILLEGAL_TRANSITION` 之一，不得返回 500。
- 同一单据的整个生命周期**只有一个终态出口**，"被取消的单又写了平台"在结构上不可能发生。

### D-02 预占存在区间与创建时点

- 预占（`budget_reservations`）在 **confirm** 时创建，**不是** approve、不是执行前。
- 预占只可能存在于 `PENDING_APPROVAL` 与 `APPROVED` 两个状态。
- `DRAFT` 阶段无预占：`DRAFT` 的 cancel/expire 路径上的"释放HELD"是**幂等空操作**，不得报错、不得创建负额预占、不得写负数 R。
- 减额（`delta <= 0`）**不创建预占**，只在核验 MATCHED 后由额度服务持锁调减 B。
- 执行前**不再新建预占**，避免同一笔增额被二次占用；执行前只做额度复检。
- 结论：`HELD` 的创建、结算、释放三处与状态一一对应，不存在"申请单已终态但预占悬空"。

### D-03 safe-retry沿用原申请与原执行单

- safe-retry **不新建**申请单、**不新建**执行单、**不新建**幂等账记录。
- 沿用原 `idempotency_key` 作为业务幂等；平台侧使用**新的** `platform_request_key`（新 attempt 行，新稳定请求键）。
- 只允许从**已定性的 `FAILED`** 发起；`UNKNOWN` 一律不允许（UNKNOWN 只能对账）。
- 发起前必须全部复检通过：原幂等键无在途尝试、错误分类 `retryable=true`、现值与申请前一致或差异可解释、动作在重试白名单、当前策略版本与审批仍有效。
- **资金增加类动作默认不在重试白名单**，且不设静默豁免。
- 守卫须先按 D-06 解除隔离才能重新领取；历史 attempt 全部保留，可区分首次与重试。
- safe-retry 是显式人工命令，**不是**消息自动重放。

### D-04 UNKNOWN的两种来源与前端投影

UNKNOWN 有两个来源，前端表达不同，但**都不重发、不计成功、不计失败**：

| 事实来源 | 执行单内部态 | 前端任务状态 | receipt.accepted | receipt.verification | error.code | retryable |
|---|---|---|---|---|---|---|
| 提交未知（无受理证据） | UNKNOWN | `EXECUTING` | `null` | `UNKNOWN` | `RESULT_UNKNOWN` | `false` |
| 已受理回读未知 | UNKNOWN | `VERIFYING` | `true` | `UNKNOWN` | 无 | `false` |

- 两种 UNKNOWN **都保留 HELD 预占**，**都把目标守卫转 QUARANTINED**。
- 前端**不得**收到私有新增的状态枚举。`UNKNOWN` 只能通过 `verification=UNKNOWN` 与 `error.code=RESULT_UNKNOWN` 表达，任务状态保持 `EXECUTING` / `VERIFYING`。
- 19册 A22 的"V8显示UNKNOWN"按此理解为"显示结果未知的可解释文案与最后核对时间"，**不是**新增状态枚举；A22 措辞修订归 R00-04（见 D-14、X-01）。
- 若未来确需独立状态值，必须走联合升级流程：前端类型、校验器、OpenAPI、UI 同时升级，后端不得私自扩枚举。

### D-05 核验期不可得与提交不可得在守卫上一视同仁

- 执行单进入 `UNKNOWN` **一律**把目标守卫（`target_execution_guards`）转 `QUARANTINED`，覆盖提交未知与回读未知两条路径。
- 租约过期**不解除隔离**，只恢复"调度与查询资格"；`QUARANTINED` 状态下任何新写领取直接返回 409 `TARGET_QUARANTINED`。
- 回读长期 UNKNOWN 超过核验窗口 → 转 `reconciliation_tasks`，**保持 UNKNOWN 与 QUARANTINED**，不降级为 `FAILED`。
- 顺序保证以数据库守卫为准，不依赖队列顺序或 Redis 锁；Redis 锁丢失不影响正确性。

### D-06 释放预占与解除隔离的证据等级

冻结三档证据，并规定每档允许的动作。**状态字符串本身不是证据。**

| 等级 | 含义 | 允许 | 必要条件 |
|---|---|---|---|
| **E2** | 已执行 | 结算预占 `SETTLED`、解除隔离、确认为生效 | 平台回执 `accepted=true` **且** 独立回读 `MATCHED` **且** `observed_value` 与 `verified_at` 均落库 |
| **E1** | 明确未执行 | 释放预占 `RELEASED`、解除隔离、定性为未执行 | 平台明确拒绝回执（`accepted=false` 且错误分类已落库）**或** 对账定性 `CONFIRMED_NOT_EXECUTED` 且带平台侧证据 **或** 独立回读证明现值与申请前一致**且**无任何受理证据 |
| **E0** | 不足以定性 | 无 | — |

- **E0 明确禁止**：结算预占、释放预占、解除隔离、再次发起写请求、自动重试。
- E0 典型事实：HTTP 200 但无回执语义、连接超时、进程在响应前崩溃、本地读超时、只有 `FAILED` 状态字符串而无拒绝或查单证据、MISMATCH 但存在受理证据。
- MISMATCH 但有受理证据时：**保留预占与隔离**，按实际回读值对账入账；**不得**按 `FAILED` 字符串直接释放。
- E1/E2 的证据必须落库可核对（对账任务的 `resolution` 与证据引用），不能只存在于日志。
- 解除隔离时若为 E1 同时 `RELEASED`，若为 E2 同时 `SETTLED`；**没有只解除隔离而不结算也不释放的第三种出口**。
- "证明未发送"（attempt 从未进入 `SENT`，或进入 `SENT` 后由平台查单证实未受理且有查单证据）才允许重新领取写请求。

### D-07 外部超限事实可入账

- `budget_ledgers` **不设** `CHECK (B + R <= limit)`；`B` 大于 `limit` 的真实事实**可以入库**并产生对账差异与告警。
- 上限校验**只对新增预占生效**，且必须在额度桶行锁内执行 `B + R + delta <= limit`。
- 同步器发现平台侧人工改动 → 串行入账（写 B 与额度变动记录）+ 产出对账差异 + 告警。
- 超限期间：**新增额拒绝**（不产生新预占）；**已批准未执行的增额必须复检**，复检不通过则该单**不得执行**，置 `FAILED`（可按 E1 释放预占，因尚未发送），并要求人工重新申请。
- 减额：仅在核验 MATCHED 后调减 B。
- 边界声明：配置预算额度 ≠ 真实消耗。系统只承诺"经本系统的写入必不越限"，不承诺实际消耗绝对不越限；外部改动必有差异告警。

### D-08 inbox恢复判定表

重投消息时按 `inbox 状态 × attempt 状态 × 守卫状态` 三元组决定允许动作。表内取值与机器清单 `inboxRecovery` 逐格一致：

| inbox | attempt | guard | actions | 说明 |
|---|---|---|---|---|
| PROCESSED | ANY | ANY | ACK_ONLY | 只有已处理才可直接ack |
| RECEIVED | NONE | IDLE | RESCHEDULE_ONLY | 未发送且守卫空闲，受控重新调度 |
| RECEIVED | PENDING | IDLE | RESCHEDULE_ONLY | 未发送，重新调度 |
| RECEIVED | PENDING | LEASED | WAIT_LEASE | 租约未过期，不抢占 |
| RECEIVED | PENDING | QUARANTINED | QUERY_ONLY; RECONCILE | 隔离中只查与对账 |
| RECEIVED | SENT | LEASED | QUERY_ONLY; RECONCILE | 在途只查不写 |
| RECEIVED | SENT | QUARANTINED | QUERY_ONLY; RECONCILE | 隔离中只查不写 |
| RECEIVED | UNKNOWN | QUARANTINED | QUERY_ONLY; RECONCILE | 未知只查并对账 |
| RECEIVED | ACK_ACCEPTED | LEASED | PERSIST_RECEIPT; SCHEDULE_READBACK | 已受理待落账 |
| RECEIVED | REJECTED | LEASED | PERSIST_FAILED; RELEASE_BY_E1 | 明确拒绝可按E1释放预占 |

- **只有 `inbox=PROCESSED` 才可直接 ack**；其余必须先持久化恢复调度（`scheduled_tasks` 或恢复事件）再 ack。
- inbox 行的存在**不构成**平台写资格；"恢复调度"≠"再次调用平台"。
- 平台写次数 ≤ 1 的判定依据是 `execution_attempts` 的 `SENT` 记录与 `platform_request_key` 唯一性。
- 不能因为 inbox 行存在就丢弃任务，也不能把恢复调度当作再次调用平台的资格。

### D-09 灰度首写放行规则

首个真实写必须**同时**满足：

1. 账户能力**六阶段全 PASS**，不可跳级：`PATH_VERIFIED → SCOPE_GRANTED → ACCOUNT_AUTHORIZED → BACKEND_INTEGRATED → SCHEMA_VERIFIED → EXECUTION_VERIFIED`；
2. 指定**账户 × 动作 × 金额**白名单，不接受"先试一次再放开"；
3. 走**完整链路**：领取 → 提交 → 受理 → 独立回读，仅 HTTP 200 不算首写成功；
4. 在真实账户的**独立额度桶**内完成额度校验与预占；
5. 首写期间**只允许该账户 × 动作**开写，其他账户与动作仍 BLOCKED；
6. 首写失败**不降级为 Mock 或夹具**，按 D-06 定性；
7. 累计 **5 次 MATCHED**（每个声明开放动作各自 5 次）后，才进入正式开放评审。

首写放行需**业务与审批负责人显式许可**；本册、代码授权与本卡的开发授权**均不构成**该许可。

### D-10 终态集合与唯一重开例外

- command_job 终态：`SUCCEEDED` / `FAILED` / `REJECTED` / `CANCELLED` / `EXPIRED` / `BLOCKED` / `MANUAL_REQUIRED`。
- execution_order 终态：`EFFECTIVE` / `FAILED` / `CANCELLED` / `MANUAL` / `PARTIAL`。
- 终态不可被普通自动事件改写。**唯一重开例外**：`FAILED` 经 safe-retry 守卫 → `EXECUTING`（沿用原申请与执行单、新增 attempt、保留失败历史）。
- `UNKNOWN` **不是终态**，是挂起态：不允许被过期扫描或超时判死。
- `EXPIRED` 只针对未执行申请；已被 Worker 领取的单据**不得**判过期（谓词已含"无 SENT 尝试"）。

### D-11 状态转移与SQL谓词一致

- 所有转移用条件更新：`update ... set status=:to, version=version+1 where id=:id and status=:from and version=:expected`；影响行数 0 即 409，不允许先查后无条件更新。
- 状态机只接收枚举值，**禁止**裸 `obj.status = ...`；对外枚举只能来自已冻结契约。
- 每次转移追加状态流水（`from`/`to`/`actor`/`reason`/`at`），`risk_summary.checks` 逐条真实输出，不得为空数组。

### D-12 冷却与次数的事实源

- 冷却与次数的**事实源是 PostgreSQL** 的成功执行与核验记录；Redis 只是加速。
- Redis 键丢失或重启**不能**解除冷却，必须回库复检。
- 计数检查与新增执行资格必须在**同一受控路径**内竞争，避免并发超发。
- 冷却以"回读 MATCHED 时间"为起点。

### D-13 UNKNOWN期间的前端表现与禁止重放

- UNKNOWN 期间任务在列表保持**进行中样式**，**不进入**成功或失败计数。
- 详情必须展示"对账中/结果未知"、**最后核对时间**与**核对入口**，不能只显示普通执行中。
- 用户不能再次提交（423 LOCKED / 409 TARGET_QUARANTINED）。
- **写请求不自动重放**；断线重连不重放写。

本卡发现的跨册差异逐条登记并指定归属卡，**不在越界分册直接改写**：

## 2. 关键量与公式

- 额度桶：`B` = 已核验确认的计划配置预算合计（含暂停计划）；`R` = 未结算增额预占合计；`delta = max(new - old, 0)`。
- 新增预占校验（额度桶行锁内）：`B + R + delta <= limit` 通过才写 `HELD`。
- 增额核验 MATCHED（同一事务）：`B += delta`、`R -= delta`，预占置 `SETTLED`。
- 减额核验 MATCHED（同一事务，持锁）：直接调减 `B`，**不**创建预占，**不**产生负额预占。
- 锁顺序固定：租户 → 额度桶 → 目标守卫 → 业务单（按 id 排序），避免死锁。
- 一个用例最多三类事务：读事务（短）、决策事务（状态推进 + 预占 + outbox，短、不跨外部调用）、落账事务（外部结果回来后记账，短）。**外部 HTTP 永远在事务外。**

## 4. 真实用例登记

机器清单 `funds-recovery-contract.json` 的 `acceptanceCases` 登记 **38 项**规格子场景，覆盖 19册 A17–A25、A33、A36，每项含 `setup`/`action`/`expected`/`evidence` 与所依据的决定编号，状态一律为 `PLANNED_REAL_TEST`。

## 7. 复盘

1. 资金安全的关键不是"状态多"，而是"**每个不确定事实都有唯一归属出口**"。D-06 把"能否释放预占/解除隔离"从状态字符串转成证据等级，正是为了杜绝"超时当失败"式误释放。
2. 竞争场景必须落到**同一条 SQL 谓词**才可实现。散文里的"与领取使用同一条件竞争"无法被代码验证，冻结时必须给出可执行谓词。
3. 守卫是幂等与串行的最后一道闸：它必须在提交未知与回读未知两条路径上表现一致，否则会出现"已知在途却允许下一个写"的缺口。
4. inbox 行的存在不构成平台写资格。把恢复调度与再次写平台分开，才能让"平台写次数 ≤ 1"在崩溃点全覆盖下成立。
5. 外部越界是**事实**不是错误：账本必须能记录真实的超限值，否则同步器只能丢弃事实或把事实挡在库外。
6. 灰度首写是最容易被"跑一次看看"绕过的一步，因此把六阶段能力、账户×动作×金额白名单、完整链路、5 次 MATCHED 与人工许可同时写死。
7. 跨册措辞冲突按归属卡处理，本卡只登记与给出口径，避免越界改写他人分册造成无声漂移。
