# 09 安全、多租户与审计

R00-02的认证函数签名、调用前置、最小权限与撤权检查见[数据库与认证冻结规格](../contracts/R00-02-数据库与认证规格.md)及[机器可核对清单](../contracts/database-auth-contract.json)。函数面是实施规格；数据库执行/攻击测试仍由M0验收。

本册规定认证、鉴权、租户隔离、密钥管理、隐私保护、审计和交付形态。安全设计按"防内部误操作和防外部攻击同等重要"处理——这个系统手握广告账户的花钱权限，越权和重复操作的代价是真金白银。

## 1. 认证体系

### 1.1 应用会话（Web 端）

- 登录方式：邮箱 + 密码，邮箱 + 验证码（6 位邮件码）。密码哈希 argon2id；验证码邮件带节流（60 秒重发、每日上限、尝试次数上限、challenge 一次性）。
- 会话形态：服务端会话事实存 PostgreSQL sessions 表，Redis 仅缓存会话主体，浏览器只持不透明随机 session id（至少 128 位熵），Cookie 属性 HttpOnly + Secure（生产 HTTPS）+ SameSite=Lax；会话滑动续期，绝对生命周期上限（如 7 天）强制重新登录，支持服务端立即吊销（登出、改密、管理员停用、批量踢下线），吊销以数据库标记为准，缓存作废只是加速。
- 不用把完整 JWT 内容暴露在前端：不透明 id 泄露后服务端可即时作废；JWT 只作为内部服务令牌（API 调 Worker 内部接口、SERVER_POLICY 任务身份）用短时效签名令牌。
- 登录防护：失败次数限制（按邮箱 + IP）、验证码兜底、登录事件审计；不向未登录侧透露"邮箱是否注册"（统一模糊提示）。

### 1.2 CSRF 与 CORS

此节为目标实现，当前ApiClient尚未获取/注入CSRF头。前后端必须作为19册F01/R01联合交付；登录前挑战的获取方式、登录后轮换、失败恢复与跨域Cookie可读方式在R00冻结。不能先在后端强制该头，再宣称现有前端已可联调。优先同源反代；分域部署时由受控JSON接口返回会话绑定令牌，不假设app域可读取api域的host-only Cookie。

- Cookie会话的所有写请求必须带会话/预认证挑战绑定的 `X-CSRF-Token`；服务端比较摘要，不一致拒绝。R00选用受控GET `/v1/auth/csrf`取得令牌，兼容分域host-only Cookie；不依赖前端读取API域csrf_token Cookie。令牌轮换和失败恢复见实施基线，F01接线尚待复核。
- CORS 精确白名单（scheme+host+port），允许凭证，不使用 `*`；预检在 Nginx 与应用双层放行必要头与方法。
- 写接口的安全不能依赖 Origin 检查单一手段，CSRF 令牌为主、Origin/Referer 校验为辅。

### 1.3 平台 OAuth 与未来开放 API

- 平台授权见 07 册：授权码流程、state 防 CSRF、回调单独验签。
- 后期对外开放 API（三方采购/系统对接）：颁发 Personal Access Token / OAuth2 客户端凭证，Authorization Bearer 认证；令牌按租户-应用-权限范围签发，可吊销、可限速、可设有效期；对外接口与人员会话接口共用同一套 RBAC 与数据范围鉴权。一期表结构预留，不提前开放。

### 1.4 多租户会话切换

用户挂靠多个租户时，会话绑定当前 tenant_id；切换租户走专门接口，后端重新计算权限与数据范围并签发新会话上下文，前端清空业务缓存（与前端"切换身份清空旧快照"行为一致）。服务商进入客户租户时会话带 agency 标记，所有写操作审计 actor_kind=AGENCY_STAFF 并记录真实操作人与客户租户。

### 1.5 认证引导与RLS的闭合边界

认证前不能依赖请求方传tenant_id来查询users/sessions/email_codes，也不能先开启租户RLS再期待无上下文登录自然成功。实施规格为受限认证仓储：使用独立认证连接角色，仅授予认证schema内的指定函数EXECUTE，应用业务角色无BYPASSRLS。函数只接受规范化邮箱/挑战/会话令牌哈希等必要输入，返回认证最小结果；不存在任意租户查询入口。

函数使用SECURITY DEFINER时固定 `search_path=pg_catalog,pg_temp`，表名全限定，所有者auth_fn_owner为NOLOGIN且不得授予运行账号角色成员资格；在同一迁移事务创建函数、撤销PUBLIC EXECUTE并逐签名授权，另撤销该创建角色的默认PUBLIC函数执行权。其BYPASSRLS只配认证必需表权限，不配业务表权限。R00冻结签名/守卫/授权和SQL模板，函数实现及攻击测试属于M0-06/09/11；不能把模板当作已部署。未知邮箱/认证失败写auth_events，tenant_id为空而不是0。

app_login与app_auth都不是所有者、无SUPERUSER/BYPASSRLS/CREATEDB/CREATEROLE；app_login无users/email_codes/auth_challenges/auth_events/sessions的直接表权限。app_auth仅auth schema USAGE和白名单函数EXECUTE，无基础表权限。认证函数不会自动校验“前一次密码已通过”：密码argon2id校验在可信后端，成员列表与建会话只允许认证用例在成功后调用，绝不直接映射成接受任意user_id的HTTP接口。若app_auth凭据本身失陷，不能宣称仍可防会话伪造；凭据隔离和注入防护属于明确的信任边界。

注意：自定义GUC可被持有数据库连接的角色设置，RLS基于app.current_tenant只能兜底漏租户过滤，不能防可信应用连接被完全接管；客户端tenantId永不用于设置该GUC。外键/唯一性检查也可能绕过RLS，因此必须有实际复合外键并将原始数据库错误映射为受控信息，不能回显其他租户对象是否存在。

认证成功并验证membership后才建立业务事务租户上下文；每次受保护请求复查PG会话撤销/过期和成员停用，满足“下次请求即时拒绝”。缓存不可作为吊销事实源；长期SSE也须定期验证和收到撤权事件关流。会话Cookie存随机bearer，数据库只存token_hash，与13册一致。

## 2. 鉴权模型：RBAC + 数据范围

### 2.1 双层鉴权

每个业务接口执行两步判断：

1. 动作权限：用户角色是否拥有该权限点（如 `plan.write`、`task.approve`、`budget.edit`）。
2. 数据范围：目标对象（企业/主体/店铺/账户）是否落在该成员被授予的数据范围内。

两层都通过才放行。前端页面守卫（canAccessPage）只是交互优化，不具安全意义；后端逐接口强制鉴权，不接受请求体里传入的 tenantId/role 作为依据——租户永远取自服务端会话，对象归属由数据库推导。

### 2.2 角色与典型授权矩阵

| 权限点 | OWNER 老板 | OPERATOR 投手 | AGENCY_OPERATOR 服务商 | AUDITOR |
|---|---|---|---|---|
| snapshot.read / overview.read | 全部 | 授权范围 | 被授权客户范围 | 全部（只读） |
| task.create / plan.write / budget.edit | 可配 | 是 | 是（范围严格） | 否 |
| task.approve | 是 | 否（或单独授予审批员） | 否（默认不授，客户自审） | 否 |
| policy.edit / goal.edit | 是 | 否 | 否 | 否 |
| content.write（内容 SOP 工作流） | 可配 | 是 | 可配 | 否 |
| report.publish | 是 | 可配（含草稿） | 否 | 否 |
| connection.manage | 是 | 否 | 否 | 否 |
| admin.access | 否 | 否 | 否 | 否（PLATFORM_ADMIN 专属） |

矩阵是初始模板不是硬编码：角色权限可在管理后台按租户调整，但"审批人与申请人分离""服务商默认无审批权""连接管理仅企业主"三条作为系统强制规则不可被配置关闭。系统不设独立内容制作角色，内容创作以 SOP 自动化工作流形态提供给 OPERATOR 使用，内容域权限默认并入投手角色。

### 2.3 职责分离约束（硬规则）

- 申请人不能审批自己的执行单（SERVER_POLICY 自动批准除外，且必须留策略依据）。
- 预算上调、扩大消耗、暂停重要计划三类动作即使在 AUTOPILOT 模式也强制人工审批（策略层不可配成静默通过）。
- PLATFORM_ADMIN 只管系统（账号、授权、审计、异常处理），不默认拥有任何租户的业务写权限；跨租户维护操作走专用账号 + 审批 + 全量审计。

## 3. 多租户隔离

### 3.1 隔离模型选择

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 共享库共享 schema + tenant_id + RLS | 成本低、运维简单、跨租户运营方便 | 要求纪律与 RLS 兜底 | 一期采用 |
| 每租户独立 schema | 隔离较强 | 迁移与运维成本随租户数线性增长 | 大客户特例可选 |
| 每租户独立数据库 | 隔离最强 | 成本最高、升级困难 | 私有化交付形态采用 |

### 3.2 共享库落地

- 每张业务表 tenant_id 列 + PostgreSQL RLS 策略（见 04 册 DDL）；应用连接每个事务 `SET LOCAL app.current_tenant`，连接池随事务回收设置。
- 纵深防御三层：应用查询构造必带租户条件（第一层过滤）→ RLS 策略兜底（第二层，漏写也查不到）→ 数据范围服务再按店铺/账户收窄（第三层，解决租户内横向越权）。
- 唯一约束全部以 tenant_id 打头（幂等键、native_id、邮箱归属等），防止跨租户碰撞和利用。
- Worker 任务消息携带 tenant_id，执行时建立独立会话上下文；批处理严禁跨租户复用连接上下文。
- 对象存储按 `tenant_id/...` 前缀分路径，预签名 URL 只签当前租户对象 key；客户报告公开链接使用不可猜测随机 token 且与租户私有文件分离存储。

### 3.3 双形态交付（SaaS 与私有化）

同一代码、同一镜像，用部署配置切换：

| 维度 | SaaS（开放/托管） | 私有化交付（三方采购） |
|---|---|---|
| TENANT_MODE | multi（开放注册或邀请入驻） | single（固定默认租户，无注册、无租户切换） |
| 部署 | K8s 共享集群 | 客户内网单机 Compose 或小集群 |
| 域名/TLS | 统一域名 | 客户域名，本地证书或其网关终止 |
| LLM | 商用云 API | 内网 vLLM 或客户自备密钥 |
| 平台授权 | 各租户自助 OAuth | 交付实施协助配置 |
| 升级 | 统一滚动升级 | 按交付合同节奏升级，迁移脚本兼容 |
| 数据备份 | 平台统一备份策略 | 交付物含备份脚本与操作手册 |

single 模式下 RLS、权限、审计代码照常运行（只有一个租户），不写 if 分支业务逻辑；差异仅限配置与部署编排。服务商代运营模式在 multi 形态支持，single 形态下服务商功能隐藏。

## 4. 密钥与敏感信息管理

### 4.1 分级保管

| 密钥/密件 | 存放方式 |
|---|---|
| 数据库/Redis 密码、SMTP、平台 app secret、LLM api_key | 环境变量/部署机密，不入代码库；生产由部署环境注入 |
| 平台 access/refresh token | AES-256-GCM 加密入 PostgreSQL，主密钥经环境注入；字段带密钥版本号 |
| 会话缓存、验证码节流、限流计数、守卫租约 | Redis，设置合理 TTL；会话与幂等的事实记录在 PostgreSQL |
| 对象存储文件 | 私有桶 + 短时效预签名 URL，不开放桶公共读（公开发布的报告除外，走随机 key） |

- 主密钥轮换：字段密文带 key_version，轮换用新密钥重加密（后台任务分批），旧密钥保留解密能力一段时间后吊销。
- .env.example 只放占位，真实 .env 加 gitignore；日志、错误信息、Sentry 上报前过脱敏中间件（token/secret/password/authorization/idempotency 及嵌套字段）。

### 4.2 个人信息保护

- 微信小店/抖店订单中的收货人、电话、地址：默认不采集；确需展示的客服类功能（二期）按角色授权、字段脱敏（手机中间四位掩码）、最短保留期。
- 结算、资金流水按财务敏感数据对待，只对 OWNER 与明确授权角色展示，不进 AI 上下文。
- 对话、AI 调用内容的留存周期可配置；报告与审计按业务留存要求保留，审计日志的个人信息同样最小化。
- 隐私相关能力（数据导出、删除）在单租户交付时按客户合规要求配套提供，表结构软删除 + 事实数据保留策略先预留。

## 5. 审计

### 5.1 审计范围（必须有）

- 登录成功/失败、登出、会话吊销、登录设备信息。
- 成员、角色、数据范围变更；平台连接、授权、重授、断开。
- 风控策略与经营目标的每次修改（版本前后值）。
- 执行单全生命周期：创建、确认、审批（含 SERVER_POLICY）、取消、提交、回执、回读、重试、对账定性。
- AI 自动产生的动作建议被采纳的情况（来源可追溯到 AUTOPILOT）。
- PLATFORM_ADMIN 的跨租户操作。

### 5.2 审计记录结构与使用

- audit_logs 只追加：actor（人/系统/自动化/服务商）、动作、对象、前后值快照、requestId、IP/UA、时间；不提供修改删除接口。
- 执行详情对前端呈现为时间线（申请-批准-提交-回执-回读-观察），与前端"执行记录"页结构一致；管理后台支持按对象、操作人、时间、平台回执号检索。
- 审计与告警联动：审批人=申请人尝试、越权探测（连续 403）、非工作时间大额调整、回读 MISMATCH 自动产生通知。
- 审计日志保留期不少于 1 年（可按租户合同调整），量大后按月分区。

## 6. 通知与审批触达

审批不能只等用户打开页面：

- 站内通知（notifications）支撑前端待办计数。
- 邮件：审批待办、执行失败/核验异常、授权即将到期；模板化，链接回具体任务（带登录拦截与 next 白名单，沿用前端既有规则）。
- Webhook 扩展：企业微信/钉钉群机器人作为可配置通道（老板和投手实际使用环境），只推送摘要，敏感金额按租户配置决定是否展示。
- 通知失败不阻断主流程，异步重试并记录。

## 7. 应用与基础设施安全

- Nginx 仅暴露 443（HSTS、TLS1.2+），API/Admin/Metrics 按来源限制；`/metrics`、`/admin` 仅内网/VPN；数据库、Redis、MinIO 不绑公网。
- 输入校验：Pydantic 强类型 + 金额/枚举/长度校验；SQL 只走 ORM 参数化，禁止字符串拼 SQL（原生 SQL 走 text() 绑定参数并过审查）。
- 文件上传：白名单 MIME/扩展、大小限制、病毒扫描预留（可挂 ClamAV 侧车）、上传后对象隔离、下载头防脚本执行。
- 速率限制：登录、验证码、发消息、写接口分级限流（slowapi/Nginx），429 带 Retry-After。
- 依赖安全：CI 跑依赖漏洞扫描（pip-audit）；基础镜像定期更新；容器以非 root 运行。
- 密钥与调试：生产关闭调试文档（或 /docs 仅内网+鉴权），错误响应不回传堆栈。
- 备份与泄露应急：数据库每日全备 + WAL 归档（见 10 册）；发生令牌泄露时支持按 authorization 批量吊销刷新、按会话批量踢下线。

## 8. 安全验收清单（上线门槛）

1. 越权测试：跨租户、跨店铺、跨账户、改请求体 ID 四类横向越权全部 403/404。
2. 重复执行：断网重放、双击、同幂等键不同载荷、UNKNOWN 后乱点，均无重复下单。
3. 审批绕过：伪造 APPROVED、AUTOPILOT、policy 字段的请求全部被拒。
4. 令牌安全：任何业务响应、日志、错误页抓取不到平台 token 与 Cookie。
5. 会话：登出即时失效；停用成员会话 5 分钟内失效；CSRF 头缺失写请求被拒。
6. 回读真实：生产环境不存在 source=MOCK 数据；EFFECTIVE 单 100% 有平台回执 ID 与 MATCHED 记录。
7. 数据边界：AI 上下文字段白名单抽查不含个人敏感信息；向量检索无跨租户结果。
